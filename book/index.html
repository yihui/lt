Preface

It seems that perfection is attained, not when there is nothing more to add, but when there is nothing more to take away.

—Antoine de Saint-Exupéry, Wind, Sand and Stars (1939, trans. Lewis Galantière)

Many reports end up with tables in them. Not glamorous ones: a few rows, a few columns, a title, a footnote that says “p-values are two-sided”. Getting such humble tables to look right often takes more effort than the analysis they summarize.

The lt package is my attempt to make tables boring again, in the good sense. You hand it a data frame, pipe it through a handful of small verbs, and get back a table that already looks like it belongs in a publication:

d = data.frame(
  Group = c("Treatment", "Treatment", "Control", "Control"),
  Endpoint = c("Primary", "Secondary", "Primary", "Secondary"),
  Estimate = c(0.6123, 0.7891, 0.4567, 0.5432),
  CI_Lower = c(0.4012, 0.5678, 0.2345, 0.3210),
  CI_Upper = c(0.8234, 1.0104, 0.6789, 0.7654),
  P_Value = c(0.0012, NA, 0.1234, NA)
)
lt(d) |>
  lt_group(~ Group) |>
  lt_header("Study Results", "Primary and secondary endpoints") |>
  lt_spanner(`95% CI` ~ CI_Lower + CI_Upper) |>
  lt_format(~ Estimate + CI_Lower + CI_Upper, decimals = 3) |>
  lt_sub(~ P_Value, missing = "n/a") |>
  lt_footnote("Two-sided p-value from log-rank test.", "column", ~ P_Value)

That is the whole idea. The rest of this book is about the details, and there are more of them than the pitch suggests: lt can also draw forest plots and sparklines inside cells, turn a table into an interactive explorer with filters and plain-language search, serve a million rows from R without breaking a sweat, and become an editable input in a Shiny app.

Why another table package?

The origin story is a small moment of shock. A project required gt, so I ran install.packages("gt") in a fresh R session on Linux, and watched R install one package after another, as if it were going to install half of CRAN. Some had to be compiled, and a few took ages (V8 in particular). I wondered whether I had mistyped something, because surely a table package could not need this much. That was when I learned how deep gt’s recursive dependency tree goes.

gt has a beautiful grammar of tables, and lt owes it the inspiration. DT makes tables interactive, but ships a whole JavaScript library with it. I wanted the vocabulary of the former and the interactivity of the latter in something I could install in a heartbeat and read in an afternoon. So I asked a question I keep asking: how small can this be if I only care about HTML? The answer turned out to be quite small, with a few deliberate trade-offs:

  • HTML first. In HTML I trust: it reflows, it styles with a line of CSS, and it opens on any phone. Every other format starts from HTML. PDF, PNG, and RTF can all be generated from a browser, which almost every machine already has (see 9). Once you commit to HTML, an enormous amount of complexity simply evaporates.

  • One dependency. lt imports xfun, and that is all. No sass, no V8, no htmltools.

  • A tiny runtime. R does not render the <table>. It ships your data and a short list of instructions as JSON, and a small, plain JavaScript file (about 10 KB minified, no framework, no build step) builds the table in the browser. A page full of tables loads that file once.

  • Pay for what you use. Inline plots and interactivity live in separate extensions that a page loads only when some table asks for them. A plain table never pays for sorting it doesn’t have.

I don’t want to match gt or DT feature for feature. I want to cover the table structure most reports actually need, and to show that if you are willing to trust HTML, you can go a remarkably long way with remarkably little.

How it works

flowchart LR
  A[data frame] -->|"lt() |> lt_*()"| B[("data + instructions<br>(JSON)")]
  B -->|"lt.js in<br>browser"| C[table]

1 From a data frame to a table: R describes, the browser draws.

Each lt_*() function records an instruction (format this column, group those rows, add a footnote here) on the table object without touching the data. When the table is printed, the data and instructions travel to the page as a compact JSON spec, and the runtime applies them. Because the spec is plain JSON, nice things follow:

  • Any language can drive it. All the table logic lives in the JavaScript runtime, once, and knows nothing about R. The R package is a thin front end that writes JSON; a Python or Julia package could be another, with no second implementation of the table engine, just a different keyboard for the same piano. You can also build a table straight from JavaScript (10).

  • The truth is always one hover away. The browser holds the original data, so formatting never throws values away. Hover over a cell to see its raw value, or press Alt and click the table to reveal all of them. We no longer have to argue about the right number of decimal places: readers can always look underneath, which a static PDF or image can never offer.

  • Other tools can embed an lt table, by shipping the spec and calling LT.render() (9).

1 Your First Table

A table is the one data visualization that everyone can read without a legend. This chapter shows how to make one with lt, and then how to give it a title, sensible labels, and a bit of polish.

1.1 One function, many verbs

Everything starts with lt(), which takes a data frame:

library(lt)
lt(head(mtcars))

That is already a respectable table: numbers are rounded sensibly and right aligned, and the column names are cleaned up. But the real fun begins when you pipe it into one of the lt_*() verbs. Each verb adds one instruction to the table, and you can stack as many as you like, in any order:

lt(head(mtcars[, 1:4])) |>
  lt_header("Cars, Briefly", "Four measurements of six cars") |>
  lt_format(~ disp, decimals = 0) |>
  lt_note("Data from the 1974 Motor Trend US magazine.")

Notice that your data frame is never modified. A table is the data plus a to-do list; the to-do list is carried out later, in the browser. That is why an lt table can show 160 while remembering that the real value was 160.0 (hover over a cell, or press Alt and click the table to reveal the raw values).

The verbs fall into a few families (1), which also happen to be the chapters of this book.

1 The verb families and where each is covered.

Many verbs take columns as their second argument. You can name them as a one-sided formula (~ mpg + disp), as a character vector (c("mpg", "disp")), or by position (1:2). A formula can even use the pronoun . for “the column names”, so ~ endsWith(., "_time") selects every column whose name ends in _time.

Before we go through the verbs one by one, here is the whole package in three cheat tables: one for static tables, one for interactive tables, and one for inline plots. 1.2.1 Static tables

The title reads lt_header(title = ...) because lt_header() put it there; every column header is the name of the function that shaped that column; the row-group label is lt_group(); the footnote text is lt_footnote(); and so on.

d = data.frame(
  Grp   = paste("Group", c("A", "A", "B", "B")),
  Label = c("<a href='#sec:cheatsheet'>lt(): make a table</a>",
            "lt_indent(): child A", "lt_indent(): child B", "lt_style() + lt_css()"),
  Fmt   = c(1234567.89, -0.51234, Inf, -Inf),
  Sub   = c(0, NA, 3.14, 0.0002),
  Date  = as.Date(c("2024-01-15", "2024-02-20", "2024-03-25", "2024-04-30")),
  Align = c(1, 22, 333, 4),
  Est   = c("0.6", "0.8", "0.5", "0.9"),
  CI    = c("(0.4, 0.8)", "(0.6, 1.0)", "(0.2, 0.7)", "(0.7, 1.1)")
)

tbl_static = lt(d, auto_format = FALSE) |>
  lt_group(~ Grp) |>
  lt_header(title = "lt_header(title = ...)", subtitle = "lt_header(subtitle = ...)") |>
  lt_merge(~ Est + CI, pattern = "{1} {2}") |>
  lt_spanner(`lt_spanner()` ~ Fmt + Sub) |>
  lt_label(
    Grp = "lt_group()", Label = "lt_label(old = new, ...)", Fmt = "lt_format()",
    Sub = "lt_sub()", Date = "lt_date()", Align = "lt_align()", Est = "lt_merge()"
  ) |>
  lt_html(~ Label) |>
  lt_align(~ Align, "center") |>
  lt_width(Align = "6em") |>
  lt_format(~ Fmt, decimals = 1, big_mark = ",") |>
  lt_date(~ Date, options = list(month = "short", day = "numeric", timeZone = "UTC")) |>
  lt_sub(~ Sub, missing = "n/a", zero = "—", small = 0.01, small_text = "< 0.01") |>
  lt_indent(c(2, 3), level = 1) |>
  lt_style(~ Label, rows = 4L, class = "highlight") |>
  lt_css(.highlight = list(fontWeight = "bold", color = "orange")) |>
  lt_footnote("lt_footnote() can add a footnote anywhere.", "title") |>
  lt_footnote(I("Wrap text in <code>I()</code> for raw HTML."), "column", ~ Label) |>
  lt_footnote("lt_width() sets column widths.", "column", ~ Align) |>
  lt_footnote("lt_move() can reorder columns as desired.", "column", ~ Est) |>
  lt_note("lt_note() — and lt_export() saves this table to HTML/PDF/PNG/RTF.")

1.3 Titles and labels

lt_header() puts a title, and optionally a subtitle, above the table:

lt(head(iris)) |>
  lt_header("Iris Measurements", "First six observations")

Column names are cleaned for display: dots and underscores become spaces, so Sepal.Length is shown as “Sepal Length”. Use auto_label = FALSE if you want the raw names back, or lt_label() to say exactly what a column should be called. lt_label() also accepts a named list or vector if your labels are already stored somewhere:

tbl = lt(head(iris))
tbl

lt(head(iris), auto_label = FALSE)

tbl |> lt_label(Sepal.Length = "Length (cm)", Sepal.Width = "Width (cm)")

A label does not have to be plain text. Wrap it in I() to use HTML, as shown in 4.3.

1.4 Alignment and widths

Numbers are right-aligned and text is left-aligned, which is what you want most of the time. When it is not, lt_align() takes "left", "center", or "right", and lt_width() sets how wide a column is, in any CSS unit. Call lt_width() with an unnamed argument to set the width of the whole table:

lt(head(mtcars[, 1:5])) |>
  lt_align(~ mpg + cyl, "center") |>
  lt_width("80%", mpg = "8em", cyl = "5em")

1.5 What kind of column is this?

When you explore a new data set, the first question is often “what is this column?”. With show_types = TRUE, lt() tags each column with its type, the same way a tibble does when printed: <dbl>, <chr>, <fct>, <date>, and so on. It also makes a pleasant default for tables meant for exploration (see lt_viewer() in 7.10).

d = data.frame(
  species = factor(c("cat", "dog", "owl")),
  weight = c(4.2, 18.5, 0.9),
  adopted = as.Date(c("2024-03-01", "2024-05-17", "2024-08-09")),
  vaccinated = c(TRUE, TRUE, FALSE)
)
lt(d, show_types = TRUE)

1.6 Where tables show up

An lt table is displayed wherever R can display HTML:

  • At the console, printing a table opens it in the RStudio or Positron viewer, or in your web browser otherwise. The table is scaled to fit the window, and a table that is too tall scrolls inside its frame with the header kept in view.

  • In a document, you simply print it, from a chunk of a litedown document, a knitr R Markdown document, or a Quarto document. The runtime assets are included once per page, however many tables the page holds. In a litedown::fuse() document, tables built from the same data frame also share one copy of the data, which keeps the output file small.

  • In a Shiny app, with lt_output() and render_lt() (8).

  • In a file, with lt_export(): standalone HTML, PDF, or PNG (9).

Because a table is just an object until it is printed, you can build it in a function, return it from a package, and let the caller add a few verbs of their own. That is how a package can offer tables that its users can still customize (12).

By default, NA is displayed as an em dash (—), so that a missing value is never mistaken for an empty string. To show something else everywhere, set options(lt.missing = "n/a"); to leave NA cells blank, use "". To change it for one column, use lt_sub() (2.4).

2 Formatting Values

Raw numbers are honest, which is the problem. 0.1234567891 is a true value, but no reader wants to see it. They want 12.3%, or $1,234.50, or a date that says “January 15” instead of a timestamp with a time zone attached. Formatting is how you turn honest numbers into readable ones, without changing the numbers themselves.

The good news is that lt does a lot of this before you ask.

2.1 Automatic formatting

By default, lt() formats every numeric column for you. It rounds to about four significant digits, so a value that needs decimals in one row and a million in another both look reasonable. It adds a thin-space thousands separator, uses a proper typographic minus sign (−) rather than a hyphen, and recognizes percentage columns by their names (rate_pct, Margin_percent), multiplying their values by 100 and adding a %. It also leaves year-like columns alone, so 2024 never becomes 2,024.

d = data.frame(
  Year = c(2020, 2021, 2022),
  Revenue = c(1234567.89, 2345678.12, -3456.789),
  Margin_pct = c(0.1234, 0.0567, 0.2345)
)
lt(d)

lt(d, auto_format = FALSE)

Automatic formatting is a sensible default for exploring data, but a publication table usually needs exact control. Use lt(d, auto_format = FALSE) to see the raw values, or keep auto-formatting on and override the columns you care about with the verbs below. Either way, the raw values are never lost: hover over a cell, or press Alt and click the table, to see them.

2.2 Number formatting

When you know what a column should look like, say so with lt_format(). It takes the columns and then whichever of these you need:

  • decimals: how many digits after the decimal point, always the same for every value in the column.
  • sig_digits: how many significant digits to keep, which adapts to the size of each value. This is the better choice when a column spans several orders of magnitude, such as particle masses.
  • big_mark: a thousands separator, such as ",".
  • percent: TRUE multiplies values by 100 and adds a %; "%" only adds the sign, for values that are already in percent.
  • prefix and suffix: text glued to each value, such as "$" or " kg".
d = data.frame(
  Item = c("Widget", "Gadget", "Doohickey"),
  Revenue = c(1234567.891, 987654.321, 246913.57),
  Margin = c(0.1234, 0.0567, 0.2345),
  Mass = c(0.00054858, 1.00727647, 4.00150618),
  Weight = c(1250, 340.5, 89.12)
)
lt(d) |>
  lt_format(~ Revenue, decimals = 0, big_mark = ",", prefix = "$") |>
  lt_format(~ Margin, decimals = 1, percent = TRUE) |>
  lt_format(~ Mass, sig_digits = 3) |>
  lt_format(~ Weight, decimals = 1, suffix = " kg")

Two rules of thumb. First, decimals and sig_digits are alternatives, so pick one: asking for both is an error, because they answer the same question in two different ways. Second, when you want a column left completely alone, even by automatic formatting, call lt_format() with just the columns and nothing else. That opts the column out without changing how it looks.

d = data.frame(Year = c(2020, 2021), Count = c(1234.5, 999.9))
lt(d) |> lt_format(~ Count)  # Count is no longer auto-formatted

percent = TRUE multiplies by 100, so a value of 0.25 shows as 25%. If your data already holds 25 for twenty-five percent, use percent = "%" instead; otherwise your reader sees 2500%.

2.3 Dates and times

Dates need more care, because the browser is the one that formats them. lt_date() hands each value to the browser’s own date formatting, so the output follows the reader’s locale and the options you ask for. Pass a locale such as "fr-FR" or "zh-CN", and an options list in the style of Intl.DateTimeFormat, to choose what appears: weekday, month name, hours, time zone, and so on.

d = data.frame(
  Event = c("Launch", "Update", "Release"),
  Date = as.Date(c("2024-01-15", "2024-06-30", "2024-12-01")),
  Time = as.POSIXct(c("2024-01-15 09:30:00", "2024-06-30 17:45:00",
    "2024-12-01 12:00:00"), tz = "UTC")
)
lt(d) |>
  lt_date(~ Date, locale = "fr-FR", options = list(
    weekday = "long", day = "numeric", month = "long", timeZone = "UTC"
  )) |>
  lt_date(~ Time, locale = "en-US", options = list(
    hour = "2-digit", minute = "2-digit", timeZone = "UTC"
  ))

Here is the gotcha that has bitten nearly everyone once. A plain date such as 2024-01-15 is stored as midnight in UTC. Show it in a time zone behind UTC, and the reader sees the day before. Passing timeZone = "UTC" in options tells the browser to format the date in UTC as well, so the day stays put.

Without timeZone = "UTC", a reader west of Greenwich may see 2024-01-14 for a date you wrote as 2024-01-15. For date-times, the opposite is what you usually want: leave the time zone alone so that each reader sees the time in their own zone.

Two more things. The method argument calls a specific JavaScript date method, such as "toDateString" or "toISOString", when you want one exact format rather than a locale-aware one. And for a date-time column, add hour and minute to options to show the time as well; without them, the time is dropped.

d = data.frame(Event = "Launch", Date = as.Date("2024-01-15"))
lt(d) |> lt_date(~ Date, method = "toDateString")

2.4 Substituting special values

Numbers have three awkward cases that deserve better text than a bare NA or a long string of zeros: missing values, zeros, and values so small that rounding would show them as 0.00. lt_sub() takes care of all three. Give it the replacement text for each case, and a threshold below which values count as “small”:

d = data.frame(
  Metric = c("HR", "p-value", "Events", "Rate", "Upper bound"),
  Value = c(0.62, 0.0003, 0, NA, Inf)
)
lt(d) |>
  lt_format(~ Value, decimals = 2) |>
  lt_sub(~ Value, missing = "n/a", zero = "—", small = 0.001, small_text = "< 0.001")

Notice the small_text: it reads < 0.001 rather than pretending the value is exactly zero. That honesty is the point. A reader who sees 0.00 will assume nothing happened, while < 0.001 tells them something did, and roughly how much. Inf and -Inf need no help at all, since they print as ∞ and −∞.

If every missing value in your report should look the same, set it once with options(lt.missing = "n/a") rather than calling lt_sub() for each column. lt_sub() is for the exceptions.

3 Shaping the Table

A table is not only a grid of values. It has a shape: a few columns that belong together under a shared heading, rows that form families, a child row that hangs off its parent, and a column or two that exists only to feed the others. This is the chapter where you give your table that shape.

3.1 Merging columns

Consider a row that reads “Age: 67 (100%)”. The number and the percentage belong together, so they should share a cell. lt_merge() does exactly that: the first column you name receives the combined text, and a pattern says how to put the pieces together. {1} is the first column, {2} the second, and so on.

d = data.frame(
  endpoint = c("Primary", "Secondary", "Tertiary"),
  est = c(0.61, 0.79, 0.45),
  lo = c(0.40, 0.57, NA),
  hi = c(0.82, 1.01, NA)
)
lt(d) |>
  lt_format(~ est + lo + hi, decimals = 2) |>
  lt_merge(~ est + lo + hi, pattern = "{1}<< ({2}, {3})>>") |>
  lt_label(est = "Estimate (95% CI)")

By default, the source columns (all but the first) are hidden, since their content now lives in the target. Set hide = FALSE if you want to keep them visible.

Sometimes one of the pieces is missing, and the sentence should not be left dangling with an empty parenthesis. Wrap the optional part in << and >>, and it vanishes whenever any value it refers to is missing. In the example above, the Tertiary row has no confidence interval, so the whole (lo, hi) part is dropped, while the rows that have one keep it. This is a small trick with a large payoff in real reports, where missing pieces are common.

lt_merge() uses the displayed values. Format the source columns first with lt_format(), as the example does, so that the merged text reads 0.61 (0.40, 0.82) and not the raw 0.6123 (0.401234, ...).

3.2 Column spanners

A spanner is a label that sits above a run of columns, telling the reader that these columns are one family. Name it with a formula, Label ~ col1 + col2. The columns must be next to each other, but you do not have to list them in visual order: lt reorders them to match the body.

tbl = lt(head(iris))
tbl |> lt_spanner(Sepal ~ Sepal.Length + Sepal.Width)

tbl |> lt_spanner()

If your columns already share a prefix, you may not need to name anything at all. Calling lt_spanner() with no arguments looks for a common prefix before the first . or _ and groups the columns that share it, shortening each column label to its suffix. In the example, Sepal.Length and Sepal.Width collapse under a “Sepal” spanner, and their labels become “Length” and “Width”.

3.3 Moving and hiding columns

Your data frame has the column order it has, but the report should read differently. lt_move() shuffles columns without touching the data. Name the columns to move and say where to put them with after: a column name, a position, or NULL for the very front.

lt_hide() is the quieter cousin. It removes columns from the table, but not from the data behind it. That distinction matters: a hidden column still travels with each row, so an interactive table can use it for a row’s detail pane (see 7.4). Hiding is therefore the right tool for “useful, but not on the page”.

tbl = lt(head(iris))
tbl |> lt_move(~ Species, after = NULL)

tbl |> lt_hide(~ Petal.Length + Petal.Width)

Use lt_hide() when a value helps a reader but clutters the page. If you want a column gone for good, drop it from the data frame before calling lt().

3.4 Row groups

Tables are easier to scan when rows come in families. lt_group() partitions the rows by the values of one or more columns, and removes those columns from the body so that the group labels do the work instead.

By default, groups are drawn as rowspan cells that run down the left side, which is compact and looks like the tables in many journals. But a long group label does not fit in a narrow cell, so lt switches to full-width separator rows on its own when a single text column has a label longer than 20 characters. You can force either style with sep = TRUE (separator rows) or sep = FALSE (rowspan cells). Separator rows take only one grouping column, while rowspan cells can nest several, one inside another.

d = data.frame(
  Region = c("East", "East", "East", "West", "West", "West"),
  State = c("NY", "NY", "MA", "WA", "WA", "OR"),
  City = c("New York", "Buffalo", "Boston", "Seattle", "Spokane", "Portland"),
  Population = c(8336817, 278349, 675647, 737015, 228989, 652503)
)
lt(d) |> lt_group(~ Region) |> lt_header("Cities by region")

lt(d) |> lt_group(~ Region + State)

lt(d) |> lt_group(~ Region, sep = TRUE)

Groups are sorted by default, so that identical values sit together. If your rows already come in the order you want, sort = FALSE keeps them as they are.

3.4.1 Manual groups and their order

Sometimes no column tells the story. Maybe the first three rows are the treatment arm because you know it from the study design, not because a column says so. In that case, name the row ranges yourself: "Label" = rows makes a group from a set of row numbers.

The same trick reorders groups. Pass the group labels, unnamed, to a later lt_group() call, and those groups move to the front in the order you list them.

tbl = lt(head(mtcars[, 1:4], 6))
tbl |> lt_group("First three" = 1:3, "Last three" = 4:6)

d = data.frame(
  arm = c("Placebo", "Placebo", "Treatment", "Treatment"),
  stat = c("n", "Mean", "n", "Mean"),
  value = c(30, 4.2, 31, 6.8)
)
lt(d) |>
  lt_group(~ arm, sep = TRUE) |>
  lt_group("Treatment", "Placebo")

3.5 Indentation

Hierarchies such as adverse events, where “Cardiac” contains “Tachycardia”, read best when the children are indented under their parent. lt_indent() nudges the first column of the chosen rows to the right, one level per step. Call it once for the parents and again for the children, with a deeper level.

d = data.frame(
  label = c("Any AE", "Cardiac", "Tachycardia", "Bradycardia", "GI", "Nausea"),
  n_pct = c("45 (67%)", "30 (45%)", "15 (22%)", "18 (27%)", "20 (30%)", "12 (18%)")
)
lt(d) |>
  lt_header("Adverse events", "Safety population") |>
  lt_indent(c(2, 5), level = 1) |>
  lt_indent(c(3, 4, 6), level = 2)

Indentation is about looks; it does not change which rows belong to which parent. If you also want interactive sorting to keep each child with its parent, see 7.8.

4 Footnotes, Notes, and HTML

Every good table has fine print. A number needs a caveat, a column needs a definition, a source needs credit. This chapter is about the small words that sit around your table and make the big numbers trustworthy.

4.1 Footnotes

lt_footnote() hangs a numbered footnote on whatever you point at. The where argument picks the target, and columns, rows, or match narrow it down (2).

2 The targets of lt_footnote() and how to narrow each one.

where Attaches to Narrow it with
"title" the title nothing
"subtitle" the subtitle nothing
"column" a column label columns
"spanner" a spanner label columns (the spanner)
"group" a row group label match
"body" specific cells columns and rows

Numbers go to footnotes in order of first appearance, so the count always runs 1, 2, 3 and never skips. Two footnotes with identical text share one number. The example below uses all six targets at once, which is more footnotes than any sensible table needs. Think of it as a stress test.

d = data.frame(
  Arm   = c("Treatment", "Treatment", "Control", "Control"),
  Stat  = c("n", "Mean", "n", "Mean"),
  Value = c(31, 6.8, 30, 4.2),
  SE    = c(NA, 0.42, NA, 0.38)
)
lt(d) |>
  lt_group(~ Arm) |>
  lt_header(title = "Study Results", subtitle = "Two arms") |>
  lt_spanner(Summary ~ Value + SE) |>
  lt_footnote("Source: simulated trial data.", "title") |>
  lt_footnote("Intention-to-treat population.", "subtitle") |>
  lt_footnote("Standard error of the mean.", "column", ~ SE) |>
  lt_footnote("Per-arm summary statistics.", "spanner", "Summary") |>
  lt_footnote("Received active drug.", "group", "Treatment") |>
  lt_footnote("SE is undefined for counts.", "body", ~ SE, rows = c(1, 3))

Footnotes on body cells are the sharpest tool in the box. Use rows to point at the exact cells that need the caveat, rather than footnoting a whole column that is mostly fine.

4.2 Source notes

A footnote explains one thing. A note sits in the footer and speaks for the whole table: where the data came from, what was excluded, who to blame. lt_note() adds an unnumbered line below any footnotes.

lt(head(mtcars[, 1:5])) |>
  lt_note("Data from the 1974 Motor Trend US magazine.")

Call it more than once to add more lines. Notes keep the order you gave them.

4.3 HTML in cells and labels

By default, lt treats every string as plain text and escapes it. That is a feature: a stray < in your data will not break the page, and nobody can sneak a <script> into a cell. But sometimes you really do want a link, some bold text, or a superscript.

Two tools, two jobs:

  • lt_html() marks whole columns as HTML. Use it when the data itself contains markup, like a column of links.
  • I() marks a single string as raw HTML. Use it for titles, labels, and notes. (It is the base R “as is” wrapper, so there is nothing new to learn.)
d = data.frame(
  Package = c(
    "<a href='https://cran.r-project.org/package=xfun'>xfun</a>",
    "<a href='https://cran.r-project.org/package=litedown'>litedown</a>"
  ),
  Mood = c("<b style='color:#090'>stable</b>", "<i>always evolving</i>")
)
lt(d) |>
  lt_html(~ Package + Mood) |>
  lt_header(I("Packages <sup>&#9733;</sup>")) |>
  lt_label(Package = I("Name<sup>*</sup>")) |>
  lt_note(I("See <a href='https://yihui.org/'>the author</a>."))

Raw HTML is passed through untouched. If the text comes from users you do not trust, escape it first with xfun::html_escape(), or keep it out of lt_html() columns altogether.

With footnotes for the caveats, notes for the credits, and HTML for the flourishes, the table now says everything it needs to. Next, let us make the numbers speak in pictures: 5.

5 Plots in Cells

A table is good at exact numbers. A chart is good at patterns. Why not have both in the same row? A forest plot of effect sizes is a table with a tiny chart in one column. A before-and-after comparison is a table with a dot per visit. A trend is a table with a little line running across it.

lt has three functions that draw these charts inside cells: lt_errorbar() for intervals, lt_dotplot() for a few values per row, and lt_sparkline() for a series of values per row. They are small, and they stay small on purpose: each chart is a handful of SVG shapes, drawn by the browser from the numbers in the table. No image is rendered, and no chart library is loaded.

Only the numbers travel to the page. The shapes are drawn in the browser when the table is shown. In an interactive table (7), that means only the rows on the current page are drawn, so a sparkline on a page of 10 rows costs 10 drawings, not 10,000.

5.1 Error bars: a forest plot in a column

Confidence intervals are the classic case. Each row needs three numbers: the estimate and its lower and upper bounds. Name them in a formula, estimate on the left, bounds on the right, and lt draws the point and the bar on one shared scale, so the rows are comparable at a glance:

d = data.frame(
  Term = c("Age", "Dose", "Baseline", "Sex"),
  Est  = c(0.12, -0.34, 0.45, -0.08),
  Lo   = c(-0.05, -0.52, 0.21, -0.29),
  Hi   = c(0.29, -0.16, 0.69, 0.13)
)
lt(d) |>
  lt_errorbar(Est ~ Lo + Hi, ref = 0, into = "Forest", hide = FALSE,
    axis = "Effect (95% CI)")

The ref = 0 argument draws a vertical line at zero, which is where you want a reference line for a risk difference (or ref = 1 for an odds ratio). The axis argument draws a proper axis in the footer, with tick marks at round values; pass a string to caption it, as above.

Look at the into = "Forest" argument. By default, the plot replaces the first value column, which is tidy but hides the numbers. With into, the plot gets a column of its own, and the numbers stay visible as text beside it. If the column does not exist yet, lt creates it at the end, so use lt_move() (1.3) if you want it somewhere else.

5.1.1 Several series in one cell

Sometimes one row should carry several intervals. Picture a trial with two treatment arms, both compared with placebo: you want to see both differences for each adverse event, and you want to see them on one scale. Give lt_errorbar() one estimate ~ lower + upper formula per series. Each row then stacks one bar per series, and color and labels explain which is which in a footer legend:

d_grp = data.frame(
  Term = c("Headache", "Nausea", "Fatigue"),
  D1 = c(2.1, -1.4, 3.3), L1 = c(-1.0, -4.2, 0.1), U1 = c(5.2, 1.4, 6.5),
  D2 = c(-0.5, 0.8, 1.2), L2 = c(-3.6, -2.1, -1.9), U2 = c(2.6, 3.7, 4.3)
)
lt(d_grp) |>
  lt_errorbar(
    D1 ~ L1 + U1, D2 ~ L2 + U2, ref = 0, color = TRUE,
    labels = c("Drug A", "Drug B"), axis = "Risk difference (%)"
  )

color = TRUE takes colors from the current palette. Pass a character vector such as c("#5b8ff9", "#f6903d") if you want specific ones. The bounds are hidden by default because the plot already shows them. color = FALSE, the default, draws every series in a single color, and the legend is then omitted.

Every bar in a column shares one scale. The scale runs from the smallest to the largest finite value across all the columns the plot reads, so a single extreme row squeezes the rest. Set limits = c(min, max) to choose the scale yourself, for example to match another table, or to keep a confidence interval that runs off the chart from being clipped unnoticed. Values outside the limits are pinned to the edges.

5.2 Dot plots: a few values per row

A dot plot answers a different question. Instead of an interval, each row has a handful of measurements, and you want to see where each one lands. Before and after is the everyday example: one dot for each visit, all on the same axis, so the movement is obvious even before you read the numbers.

d = data.frame(
  Group = c("Control", "Low", "High"),
  Before = c(3.1, 3.4, 3.0), After = c(3.2, 4.1, 5.2)
)
lt(d) |>
  lt_dotplot(~ Before + After, color = TRUE, stagger = TRUE, axis = "Score")

Give lt_dotplot() the value columns as a formula, one dot per column. The color = TRUE argument colors the dots from the palette and adds a legend, and axis (on by default) puts the shared axis in the footer. The title of the axis is the string you pass, here "Score".

Two dots that land on nearly the same value sit on top of each other, and one of them vanishes. That is what stagger = TRUE is for, as in the example above: it moves each column’s dot onto its own track, so both stay visible. The position up or down is cosmetic. The value still reads from left to right, and the cell grows taller to make room for the tracks.

The cell shows every column at once, so its column header should name them all. Use lt_label() to write something like "Before / After", as the example does. Otherwise a reader sees a single “Before” header over a row of dots that mean two things.

5.3 Sparklines: a trend in a cell

A sparkline is a word-sized line chart. Edward Tufte popularized the idea of putting such graphics inside a sentence, and it works just as well inside a table row. You can give lt_sparkline() a series in two ways. The first is a list-column, where each cell holds a vector of numbers:

d = data.frame(City = c("Oslo", "Cairo", "Lima"))
d$Temp = list(c(-3, -2, 1, 6, 12, 16), c(14, 15, 18, 23, 28, 31), c(19, 19, 18, 16, 15, 15))
d$Rain = list(c(49, 36, 47, 41, 53, 60), c(5, 4, 4, 1, 0, 0), c(8, 4, 2, 1, 1, 1))
lt(d) |>
  lt_sparkline(~ Temp) |>
  lt_sparkline(~ Rain, type = "bar", color = "#4caf50")

Each row is scaled to its own range by default, so the shape is what you see, and the actual values are in the cells next to it. The type = "bar" argument draws bars instead of a line, and color sets the color of either.

The second way is to spread the series over several ordinary columns, one per point, read left to right across each row. This is handier when your data are already wide, as in a quarterly report:

d_q = data.frame(
  Region = c("North", "South", "West"),
  Q1 = c(2, 5, 4), Q2 = c(4, 3, 6), Q3 = c(6, 7, 5), Q4 = c(5, 2, 8)
)
lt(d_q) |>
  lt_label(Q1 = "Quarterly sales") |>
  lt_sparkline(~ Q1 + Q2 + Q3 + Q4, type = "bar", limits = c(0, 8), color = "#4caf50")

Here the four quarter columns are hidden after the first, since their values now live in the chart. Use hide = FALSE to keep them visible.

5.3.1 A shared scale for honest comparisons

Per-row scaling makes every line fill its cell, which is pretty but can mislead. A row that moves from 2 to 3 looks just as dramatic as one that goes from 20 to 30. When the rows should be compared with each other, pass limits to put every sparkline on one scale. The example above did exactly that with limits = c(0, 8), so the North and West rows can be read against each other directly.

5.4 Sizing and layout

Each plot is a fixed pixel size by default: width and height set it, and width = 160 for lt_errorbar() is a sensible start. If you want the plot to follow its column, give a relative width such as "100%". The plot then grows and shrinks as the column is resized, which pairs nicely with the resizable columns of an interactive table (7). Use list(min = 200, width = "100%") to keep it from shrinking below 200 pixels.

Plots work in interactive tables, and they are drawn only for the visible page. Sorting a table with a sparkline in it reorders the rows and redraws their charts. Filtering keeps the charts of the rows that remain.

5.5 Where the charts live

Inline plots come from their own module, lt-plot.js, which is loaded only for tables that use one. A plain table does not pay for it. lt_dependency(plot = TRUE) (10) includes it explicitly when you embed a table elsewhere, and lt handles it for you everywhere else.

6 Styling

The default look of an lt table is deliberately plain: a rule on top, a rule below the header, a rule at the bottom, and nothing else. It is a good canvas. This chapter is about the three functions that let you paint on it: lt_style() for individual cells, lt_css() for rules that apply to the whole table, and lt_wrap() for keeping those rules from leaking into other tables on the same page.

6.1 Paint a few cells

Start with the shortcuts. lt_style() takes the columns and rows to hit, and then a handful of arguments you would otherwise have to spell in CSS: bold, italic, color, and bg. Leave columns out to cover every column, and leave rows out to cover every row.

lt(head(mtcars[, 1:4], 5)) |>
  lt_style(~ mpg, rows = 1, bold = TRUE, color = "#06c") |>
  lt_style(rows = 5, italic = TRUE, bg = "#fff3cd")

Anything else goes in the dots. Write the property name in camelCase (borderBottom) or as a quoted dash-case name (`border-bottom`), with the value as a string. Those are plain CSS properties, so you can reach for whatever the browser supports:

lt(head(mtcars[, 1:4], 4)) |>
  lt_style(~ mpg, rows = 1, borderBottom = "2px solid crimson", letterSpacing = ".1em")

6.2 Let the data pick the cells

Hard-coding row numbers works until the data changes. A better habit is to say what should be highlighted and let the table find it. Pass test, a small JavaScript function that receives the raw value of each cell and returns true for the cells that deserve the style.

The example below does exactly that. It also shows the second trick: instead of inline styles, tag matching cells with a class and write the rules once with lt_css(). The table then carries a class name per cell instead of a copy of the style, which keeps the output small.

d = data.frame(
  Endpoint = c("Primary", "Secondary", "Exploratory"),
  HR = c(0.62, 0.79, 1.05),
  P = c(0.001, 0.042, 0.38)
)
lt(d) |>
  lt_format(~ HR + P, decimals = 3) |>
  lt_style(~ Endpoint, rows = 1, bold = TRUE, color = "#06c") |>
  lt_style(~ HR, test = "v => v < 1", class = "good") |>
  lt_style(~ P, test = "v => v < 0.05", class = "sig") |>
  lt_css(.good = list(color = "green"), .sig = list(fontWeight = "bold"))

The test runs in the browser, not in R. That is what lets the highlighting survive sorting, filtering, and paging in an interactive table (7): the table re-evaluates the test whenever the rows move. The price is that test is a string of JavaScript, not an R expression, and it sees the raw value, so v < 0.05 compares numbers even if the cell shows "<0.05" after formatting.

A missing value arrives in the test as null, which makes it easy to flag the holes in your data:

d = data.frame(Site = c("A", "B", "C"), Enrolled = c(120, NA, 87))
lt(d) |>
  lt_style(~ Enrolled, test = "v => v == null", bg = "#fde2e2") |>
  lt_style(~ Enrolled, test = "v => v > 100", bold = TRUE)

By default NA cells show an em dash (1.6 explains how to change the text), so a pink background plus the dash is hard to miss.

6.3 Rules for the whole table

lt_css() is the home for everything that is not a one-off. It attaches CSS that is emitted after the built-in stylesheet, so your rules win ties.

A named argument is an inline rule: the name is a selector, the value is either a CSS string or a list of properties. Rules are scoped to the table, so .good really means .lt-table .good. In a list, property names can be written in camelCase as in lt_style().

lt(head(mtcars[, 1:3], 5)) |>
  lt_style(~ mpg, test = "v => v >= 21", class = "good") |>
  lt_css(
    .good = list(color = "darkgreen", fontWeight = "bold"),
    "tbody tr:hover" = "background: #f4f8ff",
    "th" = "text-transform: uppercase; font-size: .8em"
  )

An unnamed argument is a stylesheet: a path or a URL. Use it when the rules live in a file you maintain, such as a house style shared by every table in a report. Paths stay as written, so a relative one remains portable.

lt(d) |> lt_css("company-tables.css")

If a page holds many tables with the same lt_css(), the stylesheet is emitted once, not once per table.

6.3.1 The selectors worth knowing

Every part of a table has a class, so you can restyle anything without guessing at the structure. 3 lists the ones you will reach for most.

3 CSS selectors for the parts of an lt table.

6.4 Keep it on one table

Page-wide CSS is great until the page has two tables. lt_wrap() solves that by putting attributes on the <div> that wraps the table. Give it a class, and a stylesheet rule that begins with that class touches this table only.

lt(head(mtcars[, 1:5], 4)) |> lt_wrap(class = "striped")

.striped tbody tr:nth-child(even) td { background: #f2f6ff; }

The wrapper takes any HTML attribute, not only class. A fixed width and an id for deep links are the usual suspects:

lt(head(mtcars[, 1:4], 3)) |>
  lt_wrap(id = "cars", style = "max-width: 28em")

Repeated calls accumulate classes instead of replacing them, so a helper function can add its own class without wiping the caller’s.

6.5 Peek behind the format

One last trick needs no code. Alt-click on a table to reveal the raw value behind every cell that was formatted: 0.0012 appears next to 0.001, and an ISO timestamp next to its friendly date. Alt-double-click does the same for every table on the page. It is a cheap way to check that a format hides noise and not information.

7 Interactive Tables

A static table answers the question you thought to ask. An interactive table lets your reader ask the ones you did not. Which cars have the most horsepower per cylinder? Which species sits in the middle of the sepal lengths? Click a header, type a phrase, drag a slider, and the answer is already on the screen.

The best part is the price. Everything interactive is handled in the browser by an extension that loads only for tables that ask for it. Add lt_interactive() to one table on a page and that page pulls in the extension; leave it off and the table costs nothing extra.

library(lt)
lt(mtcars[, 1:4]) |> lt_interactive()

Click a header to sort, use the box above the table to search, and page through the rows with the controls below. Each feature is an option of lt_interactive(), and each option can be switched off with FALSE, so you only ever pay for the controls you keep.

7.1 Searching and sorting

Let’s start with the feature readers reach for first. This example combines sorting and search, with the pager limited to five rows:

d = mtcars[, c("mpg", "cyl", "hp", "wt", "gear")]
lt(d) |>
  lt_interactive(sort = ~ cyl + -mpg, pager = c(5, 10, Inf), filter = FALSE)

7.1.1 Sorting

Click a column header once to sort ascending, again for descending, and a third time to go back to the original order. Sorting uses the raw values, so numbers sort as numbers (10 comes after 9, not after 1), and dates sort in time order rather than alphabetically.

When one sort is not enough, shift-click a second header. The table then sorts by the first column and breaks ties with the second, and each header shows its place in the order.

You can also start the table already sorted. Give sort a character vector of column names, where a - prefix means descending, or a one-sided formula with the same rule (~ cyl + -mpg, for instance):

lt(mtcars[, 1:4]) |> lt_interactive(sort = c("cyl", "-mpg"), search = FALSE, filter = FALSE, pager = 5)

7.1.2 Search and the plain-language box

The search box looks for a term in every cell of every row, and keeps only the rows that match. Matching ignores case, so merc finds the Mercedes rows.

Typing a term is only the beginning. The box also reads a small, forgiving mini-language that feels a lot like English. A condition names a column (by its name, or by its label if the label has spaces), says what to check, and gives a value:

lt(mtcars[, 1:5]) |> lt_interactive(search = TRUE, pager = 5, filter = FALSE)

4 shows the phrases the box understands, each with what it keeps.

Two rules make the mini-language predictable. First, and binds tighter than or, so the last example reads as “4, or (6 and over 20)”: the comma and and group first, then or splits the alternatives. Second, any words that do not form a condition are searched as typed, so hornet still does what you would expect.

A line under the box shows how the query was read. If it reads cyl is 4 or cyl is 6 as you meant it, you are good to go; if it reads it differently, you have found a typo before the rows have a chance to mislead anyone.

Click the box to see a few random queries built from the table’s own values, and pick one to run it. It is the fastest way to learn the mini-language, and it works on any table, including tables you did not build yourself.

If the mini-language is too gentle for you, a term that mentions x is evaluated as a JavaScript expression against each raw cell value. So x > 20 keeps every row where any cell is above 20, and x == null finds the missing values. This is the power-user door, and it is open even when the friendly phrases are not enough.

The x expression runs in the browser, so it speaks JavaScript, not R. Write x == 4, not x == 4L, and x >= "2024-01-05" for dates. The same expressions must be valid R if you serve the table from R (see 7.11).

7.2 Paging

A table with thousands of rows is a wall, and a wall is not very friendly. The pager option breaks the rows into pages. Give it the page sizes to offer as a vector, and the first one is used at the start:

lt(mtcars[, 1:4]) |> lt_interactive(pager = c(3, 6, Inf), search = FALSE, filter = FALSE)

The selector offers 3, 6, or every row (the infinity symbol means all of them). A size only appears if it would actually split the table, so a short table does not show a useless pager. Use pager = FALSE to show every row with no pager at all.

Paging works with everything else. Sorting, filtering, and searching are applied first, and the pager then shows the page of the rows that survived. The row count beside the pager tells you how many rows the current view holds.

7.3 Filters

Search asks one question across the whole table. Filters ask a question about each column separately, and then keep the rows that pass all of them. Every column can carry a filter under its header, so the reader can narrow the table one dimension at a time:

lt(iris) |>
  lt_interactive(filter = list("auto", Species = FALSE), search = FALSE, pager = 5)

d = mtcars[, c("mpg", "cyl", "hp", "wt", "gear")]
lt(d) |>
  lt_interactive(
    filter = list(TRUE, mpg = "range", cyl = "checklist", gear = "select"),
    search = FALSE, pager = 5
  )

The first table above asks for filter = list("auto", Species = FALSE). The "auto" picks a filter per column from the data, and the FALSE removes the filter from Species. The second table asks for typed controls by name, one kind of widget per column, and a plain box for every other column.

7.3.1 Plain boxes

filter = TRUE puts a plain box under each header. It matches the same way as the search, but only in its own column, and it takes the same phrases without the column name. So under mpg you can type over 25, and under cyl you can type is 4 or is 6.

A plain box suits a reader who knows what to type. Typed widgets suit a reader who would rather pick from what is there. Use a box when the reader is going to type, and a widget when the reader is going to pick.

7.3.2 Let "auto" choose

filter = "auto" looks at each column and chooses:

  • a range slider for numbers, dates, and date-times (or a plain search box if every value is the same),
  • a checklist for text with at most 10 distinct values,
  • a plain box for everything else.

It is the default for lt_interactive() because it usually gets the answer right without asking. Override a single column by naming it in a list: list("auto", cyl = "select") keeps the automatic choice for every column but cyl, which gets a dropdown.

7.3.3 Typed controls

The typed controls are the widgets behind "auto", and you can ask for any of them by name:

  • "select" is a dropdown of the column’s values. It keeps the one value chosen.
  • "checklist" is a popover of checkboxes. It keeps every value whose box is ticked, so the reader can keep several at once. All ticked means no filter.
  • "range" is a two-thumb slider for the low and high end. When you do not supply the ends, they are read from the data and rounded outwards to values that bracket it nicely.

7.3.4 The funnel, and the expression box

A typed control appears as a little funnel under the column header. Click it to open a popover with the widget and an expression box side by side. The two stay in sync: move the slider and the expression updates, or type an expression and the slider follows. When you type something the widget cannot show, such as a value outside its choices, the widget hides itself rather than lie about what it is filtering.

If you want the widget without the expression box, pass a list with box = FALSE, such as list(type = "select", box = FALSE). The reader then picks from the widget’s own choices and nothing else, which is handy for a strict dropdown.

7.3.5 Range sliders, by hand and by keyboard

A range slider filters only when you let go. While you drag a thumb, the readout follows along, but the table waits. Otherwise the rows would reflow under your cursor and the thumb would jump out from under your finger.

Thumbs also work from the keyboard once they have focus. Arrow keys nudge a thumb one step at a time, and Home and End send it to the minimum and maximum. Tab to a thumb, and the table is yours.

7.3.6 Missing values

A "select" or "checklist" offers NA as a choice of its own. Pick it to keep only the rows where the value is missing, or leave it unticked to set those rows aside. The filter never hides a missing value by accident.

7.3.7 Filters on hidden columns

A column you hid with lt_hide() has no header to hang a filter on. Instead, its typed filter moves into the control bar as a labeled chip, showing the column name and the current value. Click anywhere on the chip to open its control. This is a good way to offer a filter on a value you do not want to show:

lt(mtcars[, 1:5]) |>
  lt_hide(~ mpg) |>
  lt_interactive(
    filter = list(TRUE, mpg = "range", cyl = "checklist"),
    search = FALSE, pager = 5
  )

7.4 Row detail

Sometimes a row has more to say than fits in a row. The detail option adds an expand caret to each row, and clicking it reveals the rest of that row’s story beneath it. The simplest form names the columns to show, and those can include columns you hid from the main table:

d = mtcars[, c("mpg", "cyl", "hp", "wt", "gear")]
lt(d) |>
  lt_hide(~ hp + wt) |>
  lt_interactive(pager = 5, filter = FALSE, detail = ~ hp + wt)

For full control, pass a JavaScript function wrapped in js(). It receives the row’s raw values, the formatted text, and the row number, and returns a table spec of its own. Here the detail is a small table that sorts itself:

lt(mtcars[, 1:5]) |>
  lt_interactive(
    pager = 3, filter = FALSE, search = FALSE,
    detail = js('(row, i, d) => ({
      data: { field: ["hp", "wt"], value: [d.hp, d.wt] },
      interactive: { sort: ["value"], search: false }
    })')
  )

The returned spec is an ordinary table spec, so it can carry its own interactive field. The detail table can be sorted, filtered, or paged, just like its parent.

7.5 Columns: resizing and hiding

7.5.1 Resizing

Drag the right edge of any header to widen or narrow that column. Widening a column widens the table and leaves the rest alone. Double-click the edge to fit the column to its contents, which is the quickest way to rescue a column whose header is cut short. Starting widths still come from lt_width().

lt(head(mtcars[, 1:4])) |> lt_interactive(pager = FALSE, search = FALSE, filter = FALSE) |>
  lt_width(mpg = "8em")

Use resize = FALSE to fix the widths.

7.5.2 The column menu

The hide option adds a menu that shows or hides columns. It opens from an eye button at the start of the search row, and it lists every column by its label. Uncheck one to hide its header and its cells; check it again to bring it back.

d = mtcars[, c("mpg", "cyl", "hp", "wt", "gear")]
lt(d) |>
  lt_interactive(hide = list(label = "Columns", columns = c("hp", "wt")),
    pager = 5, filter = FALSE)

Name columns to start with them hidden, as the example does, or use hide = NA to start with everything visible. Passing label swaps the eye icon for a labeled chip in the control bar, which is clearer when the reader might not know what the eye means.

Older code passes hide = TRUE to mean “show the menu”. It still works, but it will be dropped in a future release, so write hide = NA for the same effect.

7.6 Profiles: a picture of each column

A column’s header tells you its name. Its profile tells you its shape. With profile = TRUE, each column header carries a mini chart: a histogram for numbers and dates, and one bar per category for text. Text with mostly distinct values gets no chart, because a bar for each name would only be noise.

Hover over a chart to see summary statistics (min, max, and mean for numbers; the most frequent values for text), along with the count of missing values. Then filter a column, and the bars light up to show what share of each bucket your filter kept. It is a surprisingly good way to see what a filter is doing.

lt(iris) |> lt_interactive(profile = TRUE, pager = 5)

If the headers are already crowded, profile = "filter" moves each chart into its column’s filter popover instead. The popover only exists for columns with a typed filter, so pair this option with filter = "auto":

lt(iris) |> lt_interactive(profile = "filter", pager = 3, search = FALSE)

7.7 Downloading the view

The reader has sorted, filtered, and searched their way to exactly the rows they need. The download option turns that view into a file with one click. The button opens a menu of formats, CSV and RTF (a table for Word, with the title, column spanners, and notes). The file holds every row the filters and search keep, in sort order, across all pages, not just the page on screen:

d = mtcars[, c("mpg", "cyl", "hp", "wt", "gear")]
lt(d) |> lt_interactive(download = "cars.csv", pager = 5)

The file uses the displayed text by default, so 4.2 is written as the rounded figure the reader saw. If you need the underlying numbers at full precision, for re-importing into analysis code, ask for the raw values instead:

lt(mtcars) |> lt_interactive(download = list(file = "cars.csv", mode = "raw"))

Row detail is never included in the download. Pass download = TRUE for a default file name, or a string to name the file yourself (an extension in it is replaced by the chosen format’s). To offer only some formats, name them: with a single format the button downloads directly, without a menu.

lt(mtcars) |> lt_interactive(download = list(file = "cars", formats = "rtf"))

7.8 When rows have structure

Tables with row groups or indentation carry a shape that sorting could easily break. lt keeps that shape. Sorting and filtering always happen within each group or subtree, never across it, so a group header never gets separated from its rows, and an indented child never loses its parent.

With separator groups, the groups keep their order, and a group whose rows all filter out drops its header entirely:

d2 = data.frame(
  Region = rep(c("East", "West", "South"), each = 3),
  City = c("NYC", "Boston", "Philly", "LA", "Reno", "Boise", "Austin", "Miami", "Atlanta"),
  Sales = c(42, 17, 23, 55, 9, 14, 31, 48, 26)
)
lt(d2) |> lt_group(~ Region, sep = TRUE) |> lt_interactive(pager = 5)

With rowspan groups, clicking a group header reorders whole blocks, and with several group columns the view stays nested, so an inner column only reorders within its parent. The spanning cells are redrawn to match.

Indentation sorts siblings under each parent and carries each subtree along. Filtering a deep child keeps its ancestors visible, so the reader can always see where a row belongs:

d3 = data.frame(
  Item = c("Fruit", "Apple", "Pear", "Berry", "Grain", "Rice", "Oat", "Wheat"),
  Qty = c(0, 12, 7, 5, 0, 30, 8, 19)
)
lt(d3) |> lt_indent(c(2, 3, 4, 6, 7, 8), level = 1) |> lt_interactive(pager = 5)

Spanners, styles, and footnotes are no obstacle to any of this.

7.9 Long tables in a scrolling box

Sometimes you do not want a page scrollbar at all. Put the table in a box with a fixed height instead, and the table scrolls inside it. With lt_wrap(), you can set that box’s style directly. The header is sticky, so the column names, spanners, and controls stay in view however far the reader scrolls:

lt(mtcars[, 1:4]) |>
  lt_interactive(pager = FALSE, filter = FALSE) |>
  lt_wrap(style = "max-height: 14em; overflow-y: auto")

Printing an interactive table in the viewer or a browser already fits it to the window in the same way, so a tall table scrolls inside its frame rather than pushing the page around.

7.10 The data viewer

Most of the time, the table you want is the one that answers “what is in this data frame?”. lt_viewer() is that table, ready made. It is a shorthand for lt_interactive() with a few sensible defaults: each column shows its type and a profile, the column menu is on, and the title is the expression you passed:

lt_viewer(iris)

Printed at the console, a viewer opens in the RStudio or Positron pane when it is available, or in your browser otherwise. Remove the title with lt_header(NULL). Every argument of lt_interactive() also works here, so lt_viewer(iris, pager = 5) is a viewer with five-row pages.

Use lt_viewer() to explore, and lt_interactive() to publish. The viewer packs in types and profiles for the explorer’s benefit. In a report, a leaner table that says exactly what you mean usually reads better.

7.11 Large data: serving rows from R

Everything so far keeps the rows in the browser. That is fine for thousands of rows, and it starts to hurt somewhere past a hundred thousand. For data of millions of rows, lt_serve() keeps the rows in R instead. The browser asks for only the page it is showing, and each time the reader sorts, filters, searches, or turns the page, R sends back just those rows.

big = data.frame(id = 1:1e6, x = rnorm(1e6), g = sample(letters, 1e6, TRUE))
lt_viewer(big) |> lt_serve()

The app is local, built on xfun::new_app(), so it lives in your R session and serves the table while that session runs. In a Shiny app, you do not need it at all: return the table from render_lt(), and the session serves the rows.

output$big = lt_interactive(my_data) |> lt_serve() |> render_lt()

There is a price for the extra reach, and it is worth knowing before you lean on it:

  • Expressions run in R. Filter and search expressions such as x > 5 or x != "A" must be valid R. The phrases and the widgets’ own filters work in both places, and a missing value never passes an expression unless the expression is negated.
  • Substring matching uses the underlying values. Search and text filters look at the raw values rather than the formatted text, so a number is matched as its full precision, not as the rounded figure on screen.
  • Profiles and choices come from all the data. They are computed once when the app starts, so a dropdown lists every value, not just the current page. Plots drawn in cells scale to the current page.
  • Some table features are missing. Row groups, indentation, row-specific styles and footnotes, and external filter predicates do not work through the server. A JavaScript row detail sees only the current page.
  • The download fetches every row of the view. It is complete, but a huge view takes a while to arrive.

A local app is for looking at a table from your own R session: the console, RStudio, a remote session, or a notebook. It is not for publishing. A static document (R Markdown, Quarto, litedown) has no R session behind it once it is rendered, and webR or shinylive cannot run the app at all. For a published page, use lt_interactive() with the rows in the page, or bring your own server.

7.11.1 Bringing your own server

When the rows live somewhere else, such as a database or a folder of Parquet files, give lt_serve() a url instead. Your server answers the browser’s requests with JSON pages, and the table only needs to name its columns. A zero-row data frame is enough, because the first page is fetched too:

lt(data.frame(id = integer(), x = numeric())) |>
  lt_interactive() |>
  lt_serve(url = "https://example.org/rows")

The request and response format is the same protocol the JavaScript runtime speaks, and it is described in full in 10.15, in the JavaScript chapter (10). Any server that follows it can power a table, whatever it is built on.

8 Tables in Shiny

A Shiny app is a conversation: the reader changes something, R answers. lt joins in with three small pieces. lt_output() and render_lt() show a table. lt_input() lets the reader edit one. lt_update() lets the server rewrite what the reader sees.

None of the Shiny chunks in this chapter are run when the book is built, since they need a live session. Copy one into app.R and press Run App.

8.1 Showing a table

The pair works like any other Shiny output: lt_output("tbl") goes in the UI, render_lt() goes in the server.

library(shiny)
ui = fluidPage(lt_output("tbl"))
server = function(input, output) {
  output$tbl = render_lt(
    lt(mtcars) |> lt_header("Motor Trend") |> lt_interactive()
  )
}
shinyApp(ui, server)

What travels over the wire is the table spec (see 9.3), not HTML. The browser builds the <table> itself, so a reactive table redraws quickly and the page stays small. Anything you can do to a table elsewhere in this book (formats, plots, lt_interactive()) works inside render_lt(), and reactive inputs invalidate it the usual way:

output$tbl = render_lt(
  lt(mtcars[mtcars$cyl == input$cyl, ]) |> lt_interactive()
)

Pair render_lt() with lt_serve() (see 8.3) and the rows stay in R. The browser asks the Shiny session for one page at a time.

8.2 Editable tables

Sometimes the reader should answer rather than just read: fill in a dose schedule, correct a guess, tick off a plan. lt_input() turns chosen columns into editable cells, and the current data frame shows up as input$m.

library(shiny)
d = data.frame(Time = c(12, 24), Rate = c(0.8, 0.6), Note = c("a", "b"))
ui = fluidPage(
  lt_input("m", d, label = "Edit the cells:", columns = c("Time", "Rate")),
  actionButton("add", "Add row"),
  verbatimTextOutput("out")
)
server = function(input, output, session) {
  output$out = renderPrint(input$m)
  observeEvent(input$add, lt_update(session, "m", rbind(input$m, NA)))
}
shinyApp(ui, server)

A few things are worth knowing:

  • Click a cell to edit it. Enter commits and moves down, and clicking away commits too.
  • Numeric columns stay numeric. A cell that does not parse as a number is rejected, so input$m never turns into a column of strings by accident.
  • If you pass a matrix, you get a matrix back.
  • Only the columns named in columns are editable; the others are plain text.
  • Editing cannot be combined with lt_interactive() or with row groups that span rows.

8.2.1 Pushing changes from the server

lt_update(session, inputId, x) swaps in a new table. In the example above, the Add row button appends an NA row to input$m and sends it back, so the reader’s edits stay and a blank row appears. It is the same table, redrawn from data you control.

8.3 Serving big data

Million-row tables do not belong in a web page. lt_serve() keeps the rows in R and hands the browser one page at a time. Sorting, filtering, and searching happen on the server, and the table behaves as if it held everything.

big = data.frame(id = 1:1e6, x = rnorm(1e6), g = sample(letters, 1e6, TRUE))
lt_viewer(big) |> lt_serve()

At the console this opens a local server. Inside Shiny, render_lt() serves the rows from the session itself, so no extra port is needed. Either way the pager shows the size of the whole data, not just of the page.

The conversation between the table and its server is a small JSON protocol. It is documented in 10.15, in case you would rather feed a table from a database or a file than from R.

9 Exporting and Embedding

An lt table is born in a browser, but your readers are not always there. They open PDFs, paste tables into slides, and read Markdown on GitHub. This chapter is about getting a table out, and about the plain data underneath it.

9.2 Static output everywhere

Tables in a document like this one are dynamic. For output formats that cannot run scripts, such as GitHub-flavored Markdown, set the lt.lt_static option and every table is baked on the way out:

options(lt.lt_static = list(fragment = TRUE))

The list holds arguments of lt_export(). Leave the option unset and tables stay dynamic.

10 Using lt from JavaScript

You do not need R to use lt. The whole library is a few small scripts and one idea: a table is JSON. Hand the runtime a spec, get a table back. This chapter is for people building pages by hand, for apps written in other languages, and for the curious who want to see what R is quietly writing for them. Every example below is live: the code is the whole program, and the table under it is what the browser built from it.

10.1 Including lt.js

A page needs a stylesheet and a script for the core:

<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@xiee/utils/css/lt.min.css">
<script src="https://cdn.jsdelivr.net/npm/@xiee/utils/js/lt.min.js"></script>

Everything else is optional, and a page pays only for what it uses. The files below are listed in the order to load them, with the core in its place. Each name stands for a file under @xiee/utils: lt-plot.js is js/lt-plot.min.js and lt-plot.css is css/lt-plot.min.css, in the same URL pattern as the core above. Load the stylesheets in the same order too (the ones that exist).

10.2 The anatomy of a spec

A spec is a plain object. Only data is required; everything else decorates it.

6 The top-level keys of a spec.

Key What it holds
data An object of columns, each an array of values (null for missing).
header { title, subtitle }.
spanners Labels spanning groups of columns: [{ label, columns }].
row_group A column name (separator rows) or an array of column names (rowspan cells).
footnotes Numbered notes attached to a title, label, group, or cell.
notes Unnumbered source notes below the footnotes.
ops The list of operations, applied in order.
interactive Switches on sorting, search, filters, and more (10.12).
auto_label, auto_format, auto_span, auto_sep Switches for the automatic behaviors.
html_cols, class Raw-HTML columns and a scoping class.

The ops do the heavy lifting. Each is an object whose type names the operation, and they run in the order given, so format a number before you merge it into a string.

7 The operations, with the section that shows each.

type Does what
label, align, width Column labels, alignment, and column or table widths.
fmt_number, fmt_date, sub Format numbers and dates; substitute text for special values.
merge, move, hide Combine, reorder, and hide columns.
row_group, group_order, indent Manual groups, their order, and nesting.
style CSS for chosen cells.
errorbar, sparkline, dotplot Inline graphics.

The easiest way to learn the vocabulary is to let R write it: build a table in R, call lt_spec() (see 9.3), and read the JSON.

10.3 Building a table

Put LT.build(spec) in a <script> where the table should appear. This one has a title, two formatted columns, and a little interactivity.

No R needed: load lt.js, then call LT.build(spec) where the table should appear. The spec is plain JSON: data by column, and ops that format, label, and decorate it.

LT.build({
  data: {
    Item: ["Widget", "Gadget", "Doohickey"],
    Price: [1234.5, 678.9, 42],
    Margin: [0.1234, 0.0567, 0.2345]
  },
  header: { title: "Price list", subtitle: "Straight from JavaScript" },
  ops: [
    { type: "fmt_number", columns: ["Price"], decimals: 2, big_mark: ",", prefix: "$" },
    { type: "fmt_number", columns: ["Margin"], decimals: 1, percent: true }
  ],
  interactive: { pager: false, filter: false }
});

LT.build({

10.3.3 Labels

By default, column names are cleaned for display by replacing . and _ with spaces, so Sepal.Length shows as “Sepal Length”. Set auto_label: false to show the raw names, or use a label op to name specific columns.

// auto_label on by default: "Sepal.Length" displays as "Sepal Length"
LT.build({ data: iris });

// Disable auto-labeling
LT.build({ data: iris, auto_label: false });

// Explicit label overrides
LT.build({
  data: iris,
  ops: [
    { type: "label", labels: {
      "Sepal.Length": "Length (cm)", "Sepal.Width": "Width (cm)",
      "Petal.Length": "Length (cm)", "Petal.Width": "Width (cm)"
    }}
  ]
});

// Disable auto-labeling
LT.build({ data: iris, auto_label: false });

10.3.4 Alignment

Numeric columns are right-aligned and everything else left-aligned. Override with an align op:

LT.build({
  data: mtcars,
  ops: [
    { type: "align", columns: ["mpg", "cyl"], align: "center" }
  ]
});

10.4 Formatting numbers and dates

10.4.1 Auto-formatting

Numeric columns format themselves, so a bare data already looks decent. The rules, all visible in this example:

  • Values round to about four significant digits, adapting the decimals to the magnitude.
  • Large numbers get a thin-space thousands separator, and negatives get a typographic minus (U+2212).
  • A column whose name matches /%|[ _](pct|percent)$/i is read as a proportion: values are multiplied by 100 and suffixed with “%”.
  • A column named like /year/i holding 4-digit integers is left alone.
LT.build({
  data: {
    Year: [2020, 2021, 2022],
    Revenue: [1234567.89, 2345678.12, -3456.789],
    Margin_pct: [0.1234, 0.0567, 0.2345]
  }
});

Set auto_format: false to see the raw values instead:

LT.build({
  data: {
    Year: [2020, 2021, 2022],
    Revenue: [1234567.89, 2345678.12, -3456.789],
    Margin_pct: [0.1234, 0.0567, 0.2345]
  },
  auto_format: false
});

10.4.2 Numbers with fmt_number

When you want control, a fmt_number op sets the decimals and thousands separator (big_mark) per column. Add percent: true to multiply by 100 and append “%”.

LT.build({
  data: {
    Item: ["Widget", "Gadget", "Doohickey"],
    Revenue: [1234567.891, 987654.321, 246913.57],
    Margin: [0.1234, 0.0567, 0.2345]
  },
  ops: [
    { type: "fmt_number", columns: ["Revenue"], decimals: 0, big_mark: "," },
    { type: "fmt_number", columns: ["Margin"], decimals: 2, percent: true }
  ]
});

For columns that span several orders of magnitude, sig_digits keeps a fixed number of significant digits instead of a fixed number of decimals:

LT.build({
  data: {
    Particle: ["Electron", "Proton", "Alpha"],
    Mass: [0.00054858, 1.00727647, 4.00150618]
  },
  ops: [
    { type: "fmt_number", columns: ["Mass"], sig_digits: 3 }
  ]
});

If the values are already on the percent scale, use percent: "%", which appends the sign without multiplying:

LT.build({
  data: {
    Test: ["A", "B"],
    Rate: [78.5, 42.1]
  },
  ops: [
    { type: "fmt_number", columns: ["Rate"], decimals: 1, percent: "%" }
  ]
});

prefix and suffix add currency symbols or units:

LT.build({
  data: {
    Item: ["Widget", "Gadget", "Doohickey"],
    Price: [1234.5, 678.9, 42.0],
    Weight: [1250, 340.5, 89.12]
  },
  ops: [
    { type: "fmt_number", columns: ["Price"], decimals: 2, big_mark: ",", prefix: "$" },
    { type: "fmt_number", columns: ["Weight"], decimals: 1, suffix: " kg" }
  ]
});

10.4.3 Dates with fmt_date

Values can be Date objects or ISO strings. By default fmt_date calls toLocaleDateString(). Pass method to call another Date method, or locale and options for full Intl.DateTimeFormat control.

Mind the time zone. new Date("2024-01-15") is parsed as UTC midnight, but toLocaleDateString() converts to local time, so that date shows as 2024-01-14 for a reader at GMT-6. Pass options: { timeZone: "UTC" } to avoid the shift.

LT.build({
  data: {
    Event: ["Launch", "Update", "Release"],
    Date: [new Date("2024-01-15"), new Date("2024-06-30"), new Date("2024-12-01")]
  },
  ops: [
    { type: "fmt_date", columns: ["Date"] }
  ]
});

A locale and options give you, say, a Chinese long date:

LT.build({
  data: {
    Event: ["Launch", "Update"],
    Date: [new Date("2024-01-15"), new Date("2024-06-30")]
  },
  ops: [
    { type: "fmt_date", columns: ["Date"], locale: "zh-CN",
      options: { year: "numeric", month: "long", day: "numeric",
                 weekday: "long", timeZone: "UTC" } }
  ]
});

Use method for a different Date method:

LT.build({
  data: {
    Event: ["Launch", "Update"],
    Date: [new Date("2024-01-15"), new Date("2024-06-30")]
  },
  ops: [
    { type: "fmt_date", columns: ["Date"], method: "toDateString" }
  ]
});

For date-times, include the time components in options:

LT.build({
  data: {
    Event: ["Start", "End"],
    Time: [new Date("2024-01-15T09:30:00Z"), new Date("2024-01-15T17:45:00Z")]
  },
  ops: [
    { type: "fmt_date", columns: ["Time"], locale: "en-US",
      options: { year: "numeric", month: "short", day: "numeric",
                 hour: "2-digit", minute: "2-digit" } }
  ]
});

10.4.4 Substituting values with sub

Replace missing, zero, or small values with display text. Put sub after the formatting op so it sees the numbers first.

LT.build({
  data: {
    Metric: ["HR", "p-value", "Events", "Rate"],
    Value: [0.62, 0.0003, 0, null]
  },
  ops: [
    { type: "fmt_number", columns: ["Value"], decimals: 2 },
    { type: "sub", columns: ["Value"], missing: "n/a", zero: "—", small: 0.001, small_text: "< 0.001" }
  ]
});

Infinities need a JavaScript object rather than JSON (JSON has no Infinity), and they format as the symbols themselves:

LT.build({
  data: {
    Metric: ["Lower bound", "Upper bound", "Rate", "Missing"],
    Value: [-Infinity, Infinity, 1.5, null]
  },
  ops: [
    { type: "fmt_number", columns: ["Value"], decimals: 2 }
  ]
});

10.5 Columns

10.5.1 Merging with merge

Combine several columns into one display column. The pattern uses {1}, {2}, and so on for the columns in order. Wrap a stretch in << and >> to make it conditional: it vanishes when any value inside it is missing, which is how the tertiary row below loses its empty confidence interval.

LT.build({
  data: {
    Endpoint: ["Primary", "Secondary", "Tertiary"],
    est: [0.61, 0.79, 0.45],
    ci_lo: [0.40, 0.57, null],
    ci_hi: [0.82, 1.01, null]
  },
  ops: [
    { type: "fmt_number", columns: ["est", "ci_lo", "ci_hi"], decimals: 2 },
    { type: "merge", columns: ["est", "ci_lo", "ci_hi"], pattern: "{1}<< ({2}, {3})>>" },
    { type: "label", labels: { est: "Estimate (95% CI)" } }
  ]
});

10.5.2 Spanners

A spanner groups contiguous columns under a shared header:

LT.build({
  data: iris,
  spanners: [
    { label: "Sepal", columns: ["Sepal.Length", "Sepal.Width"] },
    { label: "Petal", columns: ["Petal.Length", "Petal.Width"] }
  ]
});

Set auto_span: true to infer spanners from the column names. Names split on the first . or _, contiguous columns sharing a prefix are grouped, and the labels shrink to the suffix. A string such as "[.]" is taken as a regular expression for a custom separator.

LT.build({ data: iris, auto_span: true });

10.5.3 Widths

A width op sets column widths with any CSS length:

LT.build({
  data: mtcars,
  ops: [
    { type: "width", widths: { mpg: "10em", cyl: "5em", disp: "10em", hp: "8em" } }
  ]
});

Give it table to size the whole table. It combines with column widths:

LT.build({
  data: iris,
  ops: [
    { type: "width", table: "80%" }
  ]
});

LT.build({
  data: iris,
  ops: [
    { type: "width", table: "100%", widths: { Species: "20em" } }
  ]
});

10.5.4 Moving and hiding

A move op puts columns first (after: null) or after a named column:

LT.build({
  data: iris,
  ops: [
    { type: "move", columns: ["Petal.Length", "Petal.Width"], after: null }
  ]
});

A hide op drops columns from view but not from the spec. Their values still travel with the row, so anything that reads the whole row, such as an interactive table’s detail, can use them.

LT.build({
  data: iris,
  ops: [
    { type: "hide", columns: ["Petal.Length", "Petal.Width"] }
  ]
});

10.6 Inline plots

Three ops draw small SVG graphics in cells. They come from the graphics module (lt-plot.js, loaded before the core script), and the SVG is built in the browser from the numbers, so an interactive table draws only the rows on the current page.

10.6.1 Error bars

errorbar draws a point at the estimate with a bar (and end caps) from the lower to the upper bound, on a scale shared by the column. columns lists the value column, lowers and uppers the matching bounds; the plot replaces the first value column’s cells, so hide the bounds. min and max set the shared scale, ref draws a vertical reference line, and width and height size each SVG. axis: true adds a shared axis to the footer (ticks and labels at round values, plus gridlines in the cells), which axis_label captions.

LT.build({
  data: {
    Term: ["Age", "Dose", "Baseline", "Sex"],
    Est:  [0.12, -0.34, 0.45, -0.08],
    Lo:   [-0.05, -0.52, 0.21, -0.29],
    Hi:   [0.29, -0.16, 0.69, 0.13]
  },
  ops: [
    { type: "hide", columns: ["Lo", "Hi"] },
    { type: "errorbar", columns: ["Est"], lowers: ["Lo"], uppers: ["Hi"],
      min: -0.6, max: 0.7, ref: 0, axis: true, axis_label: "Effect (95% CI)" }
  ]
});

Several series stack in one cell: give columns, lowers, and uppers one entry per series, and colors and labels to key them in a footer legend.

LT.build({
  data: {
    Term: ["Headache", "Nausea", "Fatigue"],
    D1: [2.1, -1.4, 3.3], L1: [-1.0, -4.2, 0.1], U1: [5.2, 1.4, 6.5],
    D2: [-0.5, 0.8, 1.2], L2: [-3.6, -2.1, -1.9], U2: [2.6, 3.7, 4.3]
  },
  ops: [
    { type: "hide", columns: ["L1", "U1", "D2", "L2", "U2"] },
    { type: "errorbar",
      columns: ["D1", "D2"], lowers: ["L1", "L2"], uppers: ["U1", "U2"],
      colors: ["#5b8ff9", "#f6903d"], labels: ["Drug A", "Drug B"],
      min: -5, max: 7, ref: 0, axis: true, axis_label: "Risk difference (%)" }
  ]
});

10.6.2 Sparklines

sparkline draws a per-row series as a small line or bar chart. columns is either a single list-column (each cell a numeric array) or several numeric columns read across the row (hide all but the first). kind is "line" (default) or "bar", color styles the line or bars, and min and max set a shared vertical scale (by default each row scales to its own range).

LT.build({
  data: {
    City: ["Oslo", "Cairo", "Lima"],
    Temp: [[-3, -2, 1, 6, 12, 16], [14, 15, 18, 23, 28, 31], [19, 19, 18, 16, 15, 15]],
    Rain: [[49, 36, 47, 41, 53, 60], [5, 4, 4, 1, 0, 0], [8, 4, 2, 1, 1, 1]]
  },
  ops: [
    { type: "sparkline", columns: ["Temp"] },
    { type: "sparkline", columns: ["Rain"], kind: "bar", color: "#4caf50" }
  ]
});

10.6.3 Dot plots

dotplot puts one dot per column on a shared scale, so a row with N columns shows N dots laid out by value. columns lists the value columns (hide all but the first), colors gives one color per column, and labels names them in a footer legend (the column names by default). min, max, axis, and axis_label work as for error bars. Since the cell shows every column, label its header with all the names joined, using a label op.

LT.build({
  data: {
    Group:  ["Control", "Low", "High"],
    Before: [3.1, 3.4, 3.0],
    After:  [3.3, 4.1, 5.2]
  },
  ops: [
    { type: "hide", columns: ["After"] },
    { type: "label", labels: { Before: "Before / After" } },
    { type: "dotplot", columns: ["Before", "After"],
      colors: ["#999999", "#1a9641"], labels: ["Baseline", "Follow-up"],
      min: 2.5, max: 5.5, axis: true, axis_label: "Score" }
  ]
});

stagger: true spreads near-equal dots onto separate tracks so they do not overlap, and the cell grows taller to fit one track per column:

LT.build({
  data: {
    Group:  ["Control", "Low", "High"],
    Before: [3.1, 3.4, 3.0],
    After:  [3.2, 4.1, 5.2]
  },
  ops: [
    { type: "hide", columns: ["After"] },
    { type: "label", labels: { Before: "Before / After" } },
    { type: "dotplot", columns: ["Before", "After"], stagger: true,
      colors: ["#999999", "#1a9641"], labels: ["Baseline", "Follow-up"],
      min: 2.5, max: 5.5, axis: true, axis_label: "Score" }
  ]
});

10.7 Row groups and indentation

10.7.1 Grouping by a column

row_group takes a column name or an array of names. An array of one name groups by that column’s values, shown as rowspan cells on the left:

LT.build({
  data: {
    Region: ["East", "East", "West", "West", "West"],
    City: ["New York", "Boston", "Seattle", "Portland", "Denver"],
    Population: [8336817, 675647, 737015, 652503, 715522]
  },
  row_group: ["Region"]
});

When the column is character and any value is longer than 20 characters, a single-column group switches to separator rows on its own, since long labels squeeze a rowspan cell:

LT.build({
  data: {
    Department: ["Cardiovascular Research", "Cardiovascular Research",
                 "Biostatistics", "Biostatistics"],
    Trial: ["ATLAS-2", "BEACON", "PRIME-1", "NEXUS"],
    N: [450, 320, 280, 510]
  },
  row_group: ["Department"]
});

Set auto_sep: false to force rowspan mode:

// Force rowspan mode by disabling auto-detection
LT.build({
  data: {
    Department: ["Cardiovascular Research", "Cardiovascular Research",
                 "Biostatistics", "Biostatistics"],
    Trial: ["ATLAS-2", "BEACON", "PRIME-1", "NEXUS"],
    N: [450, 320, 280, 510]
  },
  row_group: ["Department"],
  auto_sep: false
});

Several columns nest as hierarchical rowspan cells:

LT.build({
  data: {
    Region: ["East", "East", "East", "West", "West", "West"],
    State: ["NY", "NY", "MA", "WA", "WA", "OR"],
    City: ["New York", "Buffalo", "Boston", "Seattle", "Spokane", "Portland"],
    Population: [8336817, 278349, 675647, 737015, 228989, 652503]
  },
  row_group: ["Region", "State"]
});

Pass a plain string (rather than an array) to always use separator rows:

LT.build({
  data: {
    arm: ["Placebo", "Placebo", "Treatment", "Treatment"],
    stat: ["n", "Mean", "n", "Mean"],
    value: [30, 4.2, 31, 6.8]
  },
  row_group: "arm"
});

A group_order op reorders separator groups:

LT.build({
  data: {
    arm: ["Placebo", "Placebo", "Treatment", "Treatment"],
    stat: ["n", "Mean", "n", "Mean"],
    value: ["30", "4.2", "31", "6.8"]
  },
  row_group: "arm",
  ops: [
    { type: "group_order", order: ["Treatment", "Placebo"] }
  ]
});

10.7.2 Manual groups

Define groups by hand, with 1-based row indices, using row_group ops:

LT.build({
  data: mtcars,
  ops: [
    { type: "row_group", label: "First three", rows: [1, 2, 3] },
    { type: "row_group", label: "Last three", rows: [4, 5, 6] }
  ]
});

10.7.3 Indentation

An indent op nests rows to show hierarchy:

LT.build({
  data: {
    label: ["Any AE", "SOC: Cardiac", "Tachycardia", "Bradycardia", "SOC: GI", "Nausea"],
    n_pct: ["45 (67%)", "30 (45%)", "15 (22%)", "18 (27%)", "20 (30%)", "12 (18%)"]
  },
  ops: [
    { type: "indent", rows: [2, 5], level: 1 },
    { type: "indent", rows: [3, 4, 6], level: 2 }
  ]
});

10.8 Styling

10.8.1 Styling cells

A style op applies CSS to cells chosen by columns and/or 1-based rows:

LT.build({
  data: {
    Endpoint: ["Primary", "Secondary", "Exploratory"],
    HR: [0.62, 0.79, 0.91],
    P: [0.001, 0.042, 0.38]
  },
  ops: [
    { type: "fmt_number", columns: ["HR"], decimals: 2 },
    { type: "fmt_number", columns: ["P"], decimals: 3 },
    { type: "style", columns: ["P"], rows: [1, 2], css: "font-weight:bold;color:#06c" },
    { type: "style", columns: ["HR"], rows: [1], css: "background:#e8f4e8;border-bottom:2px solid #4a4" }
  ]
});

10.8.2 Conditional styling

Give test a JavaScript function and the style applies where it returns true. The function receives the raw (pre-format) value. Use class to assign a CSS class instead of inline css:

LT.build({
  data: {
    Endpoint: ["Primary", "Secondary", "Exploratory"],
    HR: [0.62, 0.79, 1.05],
    P: [0.001, 0.042, 0.38]
  },
  ops: [
    { type: "fmt_number", columns: ["HR", "P"], decimals: 3 },
    { type: "style", columns: ["HR"], test: v => v < 1, class: "good" },
    { type: "style", columns: ["P"], test: v => v < 0.05, css: "font-weight:bold" }
  ]
});

.lt-table .good { color: green; }

Leave out columns to test every cell, such as to highlight missing values:

LT.build({
  data: {
    arm: ["Treatment", "Control", "Treatment"],
    n: [30, null, 28],
    response: [0.67, null, 0.71]
  },
  ops: [
    { type: "style", test: v => v == null, class: "na" }
  ]
});

.lt-table .na { background: #fee; }

10.8.3 Scoping a style to one table

A top-level class (a string or an array of names) lands on the table’s container, so a stylesheet can target one table and not every lt table on the page. Here the container is tagged striped, and a rule keyed on .striped zebra-stripes this table alone:

LT.build({ data: mtcars, class: "striped" });

.striped tbody tr:nth-child(even) td { background: #f2f6ff; }

10.9 HTML content

Everything is HTML-escaped by default, so <, >, and & show as typed. Two mechanisms opt into raw HTML:

  • Body cells: set html_cols to true (all columns) or an array of column names, and those cells are emitted verbatim.
  • Text fields (title, subtitle, column and spanner labels, footnote and note text): pass a one-element array instead of a string. "<b>x</b>" is escaped; ["<b>x</b>"] is raw. This is what R’s I() becomes in the JSON.
LT.build({
  data: {
    Package: [
      "<a href='https://cran.r-project.org/package=lt'>lt</a>",
      "<a href='https://cran.r-project.org/package=xfun'>xfun</a>"
    ],
    Status: ["<b style='color:#090'>stable</b>", "<i>active</i>"]
  },
  html_cols: ["Package", "Status"],
  header: { title: ["Packages <sup>&#9733;</sup>"] },
  ops: [
    { type: "label", labels: { Package: ["Name<sup>*</sup>"] } }
  ],
  notes: [["See <a href='https://yihui.org/'>the author</a>."]]
});

10.10 Footnotes and source notes

Footnotes are de-duplicated by text and numbered automatically. Each one has a location whose type picks a region: title (with group: "title" or group: "subtitle"), column_labels, column_spanners, row_groups, or body. The example attaches one to every kind of place:

LT.build({
  data: {
    Arm: ["Treatment", "Treatment", "Control", "Control"],
    Stat: ["n", "Mean", "n", "Mean"],
    Value: [31, 6.8, 30, 4.2],
    SE: [null, 0.42, null, 0.38]
  },
  row_group: "Arm",
  header: { title: "Study Results", subtitle: "Two arms" },
  spanners: [{ label: "Summary", columns: ["Value", "SE"] }],
  footnotes: [
    // title and subtitle share type "title", distinguished by group
    { text: "Source: simulated trial data.", location: { type: "title", group: "title" } },
    { text: "Intention-to-treat population.", location: { type: "title", group: "subtitle" } },
    // a column label
    { text: "Standard error of the mean.", location: { type: "column_labels", columns: ["SE"] } },
    // a spanner label
    { text: "Per-arm summary statistics.", location: { type: "column_spanners", spanners: ["Summary"] } },
    // a row-group label
    { text: "Received active drug.", location: { type: "row_groups", match: "exact", values: ["Treatment"] } },
    // specific body cells (columns + 1-based rows)
    { text: "SE undefined for counts.", location: { type: "body", columns: ["SE"], rows: [1, 3] } }
  ]
});

notes are unnumbered source lines below the footnotes:

LT.build({
  data: mtcars,
  notes: ["Data from the 1974 Motor Trend US magazine."]
});

10.12 Interactive tables

With lt-interactive.js on the page, a spec carrying an interactive object gets the requested controls. Every field is optional. 8 lists them; the rest of the section explains each.

8 Fields of interactive.

Field Controls
sort Click-to-sort headers and an initial order.

resize Dragging column edges.

10.12.1 Sorting

Headers sort on click: ascending, then descending, then back to unsorted. Shift-click adds a column as a tie-breaker. An array requests an initial order, each element a column name, "-name" for descending, or a { col, dir } object. false turns sorting off.

10.12.2 Searching

The search box matches any cell, case-insensitively, against the displayed text (false hides it). It also reads plain language:

  • A condition names a column (by name or label, spaces allowed), then an operator: over / above / more than, under / below / less than, at least, at most, between 5 and 10, is / equals, is not, contains, or does not contain (the column name is optional for the last).
  • Join conditions with and, ,, or ;; use or for alternatives. and binds tighter, so cyl is 4 or cyl is 6 and mpg over 25, cyl is 4 both do what they look like.
  • A term that mentions x, such as x > 20, is evaluated as a JavaScript expression on the raw cell value.
  • Anything else is searched as typed, and a quoted phrase stays whole.

The box echoes how it read your query, and its placeholder and dropdown offer random example queries built from the table’s own values.

10.12.3 Filters

filter is { default, cols }. default applies to every visible column left unnamed, and cols maps a column to its own spec. A spec is one of:

  • true: a plain box, matching that column the way the search does.
  • { type: "select" }: a dropdown that keeps one chosen value.
  • { type: "range" }: a two-thumb slider.
  • { type: "checklist" }: a popover of checkboxes that keeps every checked value (all checked means no filter).
  • { type: "auto" }: picks the control from the data. Numbers get a slider (a plain box if constant), strings with at most 10 distinct values get a checklist, anything else gets a box.
  • false: no filter for that column, even under a default.

Choices and ends are read from the column, or set with choices, or min and max; selected seeds the dropdown’s value or the checklist’s checked set. So { default: true } boxes every column, { cols: { mpg: true } } boxes one, and { cols: { cyl: { type: "select" } } } gives cyl a dropdown.

LT.build({
  data: mtcars,
  interactive: { filter: { cols: { mpg: true } }, pager: [3, 6, 0], resize: true }
});

Typed filters: a dropdown on cyl, a range slider on wt, a checklist on hp, and a plain box for the rest. A typed filter on a hidden column has no header to sit under, so it moves into the control bar as a labeled chip (click anywhere on the chip to open it). Here gear is hidden yet still filterable.

LT.build({
  data: mtcars,
  interactive: {
    search: false, pager: 6,
    hide: { hidden: ["gear"] },
    filter: { default: true, cols: {
      cyl: { type: "select" }, wt: { type: "range" }, hp: { type: "checklist" },
      gear: { type: "select" }
    } }
  }
});

With { type: "auto" } as the default, each column gets the control that suits its data, a slider for the numbers and a checklist for Species:

LT.build({
  data: iris,
  interactive: { search: false, pager: 5, filter: { default: { type: "auto" } } }
});

A column mapped to false gets no filter even under the "auto" default. Here Species is left out:

LT.build({
  data: iris,
  interactive: {
    search: false, pager: 5,
    filter: { default: { type: "auto" }, cols: { Species: false } }
  }
});

A range slider updates its readout as you drag but applies the filter on release, so the table does not reflow under your cursor. Focus a thumb to use the keyboard: arrows step it, Home and End jump to the ends. With min, max, and step omitted, they come from the data as round, data-bracketing values.

10.12.4 Paging

pager is an array of page sizes to offer, the first being the initial size; 0 means every row on one page. Omit it for the default sizes, or set false to show all rows with no pager.

10.12.5 Resizing and hiding columns

resize: true lets readers drag a column’s right edge (double-click the edge to fit the column to its content). hide adds an eye button at the start of the search row that opens a checklist of every column by its displayed label. hide: true starts with all shown; { hidden: [...] } starts the named columns hidden, though all stay listed so any can be toggled back.

LT.build({
  data: mtcars,
  interactive: { hide: { hidden: ["hp", "wt"] }, pager: 5 }
});

10.12.6 Row detail

detail adds an expand caret to each row and builds a table below it on first expand. Give an array of column names for a one-row table of their displayed values (hidden columns included), or a function (row, index, display) => spec (or the name of a global one) that returns the spec. row holds the raw values and display the formatted text, both keyed by column name and covering every column. The returned spec is an ordinary table spec, so it can carry its own interactive field to make the detail table sortable, filterable, or paged.

LT.build({
  data: iris,
  ops: [{ type: "hide", columns: ["Petal.Length", "Petal.Width"] }],
  interactive: { pager: false, detail: ["Petal.Length", "Petal.Width"] }
});

10.12.7 Profiles

profile draws a mini chart of each column, a histogram for numbers and dates or a bar per category for text, with summary statistics as a tooltip. The bars highlight the rows the filters keep. "header" puts it in the column header, "filter" in the filter popover (only for columns that have one).

LT.build({
  data: mtcars,
  interactive: { profile: "header", pager: 5 }
});

10.12.8 Downloading the view

download adds a button that saves the current view (every row the filters and search keep, in sort order, across all pages) as a file of the displayed text, in a format picked from a menu (CSV or RTF). true picks a default file name; a string sets it. { file, mode: "raw", formats: ["rtf"] } names the file, exports raw values, and limits the formats (one format downloads directly). Filter or sort first, and the file follows:

LT.build({
  data: mtcars,
  interactive: { download: "cars.csv", filter: { default: true }, pager: 5 }
});

10.12.9 Row structure

Sorting and filtering happen within each group or subtree, never across it. A separator group whose rows all filter out drops its header; a rowspan group reorders its blocks when its header is clicked and stays nested with several columns. An indent op sorts siblings under each parent and keeps a match’s ancestors visible. Spanners, styles, and footnotes are no obstacle.

LT.build({
  data: mtcars,
  row_group: ["cyl"],
  interactive: { pager: [8] }
});

10.12.10 Raw values

Formatting changes what you see, not what is stored. Hover over a cell to see its original value in a tooltip, Alt + Click a table to reveal all of its raw values, or Alt + Double-Click to toggle raw values for every table on the page.

10.13 Rendering on demand

LT.build() renders the table where its <script> sits, so it has to run while the page is parsing. LT.render(element, spec) has no such constraint: it renders into a container whenever you call it and returns the table element. Interactive tables built this way are enhanced like any other, so a table can be built lazily, say only when the reader asks:

const box = document.createElement("div"), btn = document.createElement("button");
btn.textContent = "Build a table";
btn.onclick = () => {
  LT.render(box, { data: iris, interactive: { pager: [3] } });
  btn.disabled = true;
};
document.currentScript.after(box);
document.currentScript.after(btn);

10.14 Driving a table from outside

Every enhanced table carries a small controller at el._lt, so widgets outside the table, such as a dropdown or a range slider, can filter it without the built-in boxes:

  • el._lt.filter(id, func) registers a predicate func(row) under id, where row holds the row’s raw values keyed by column; the rows kept are those for which func returns a truthy value. Call it again with the same id to replace the predicate, or with a null func to remove it. Predicates from every id, together with the built-in column filters and the search, combine with AND.
  • el._lt.refresh() re-renders the body. filter() calls it for you, so you rarely need it directly.
  • el._lt.view() returns the current view as 1-based original row indices (every row the filters and search keep, in sort order, across all pages), which is what a “download what is shown” button reads.
  • el._lt.spec and el._lt.state are there for reading. A widget can read el._lt.spec.data[col] to build its choices: the unique categories for a dropdown, the min and max for a slider.

Predicates live in the table’s state, so they survive sorting and paging. Here an outside <select> filters the table by Species:

// wire the widget up once the page (and lt.js) has loaded
const host = document.createElement("div");
document.currentScript.after(host);
addEventListener("load", () => {
  const t = LT.render(host, { data: iris, interactive: { search: false, pager: [5] } });
  const sel = document.createElement("select");
  sel.innerHTML = '<option value="">All species</option>' +
    [...new Set(t._lt.spec.data.Species)].map(s => `<option>${s}</option>`).join("");
  sel.onchange = () => t._lt.filter(
    "species", sel.value ? row => row.Species === sel.value : null
  );
  t.before(sel);
});

10.15 Server mode

When there are too many rows to ship, a table can ask a server for them instead. Load lt-server.js before lt-interactive.js, and set interactive.data_url. lt_serve() in R does exactly this (see 8.3), and any server that speaks the protocol below can feed a table, such as one backed by a database or Parquet files.

spec.data only needs the column names (empty arrays will do), because the first page is fetched too. Optional fields: data_times lists date-time columns (sent as ISO 8601 strings), data_n is the number of rows in the whole data, and data_cols holds per-column summaries for profiles and filter widgets. Without data_cols, columns get a plain filter box.

10.15.1 The request

The browser sends POST <data_url> with a JSON body, using Content-Type: text/plain to dodge a CORS preflight. The body is an object:

  • where: the rows to keep, or null for all. A condition is a leaf { col, term } or a group { op: "and" | "or", items }. A term that uses x for the cell value and is a JavaScript expression (x > 5, x == null, ["a", "b"].includes(x)) keeps the rows where it is true; one that starts with ! or is x != ... negates. Any other term is a case-insensitive substring of the cell text. If col is null, the term is tried on every visible column.
  • sort: [{ col, dir: "asc" | "desc" }, ...], most significant first, missing values last.
  • page (from 0) and size: the page wanted. size 0 means every row.
  • cols: the visible columns.
  • prof (optional): the columns whose profile bars are wanted.

10.15.2 The reply

The server answers with JSON (Content-Type: application/json, plus Access-Control-Allow-Origin if the page lives on another origin):

  • n: the number of rows in the view.
  • page: the page returned, clamped to the last page.
  • data: the page’s values by column, such as { "a": [1, 2], "b": ["x", "y"] }, with null for missing values and dates as "YYYY-MM-DD".
  • prof (optional): bar counts over the kept rows, for each column in prof.

That is the whole contract. A forty-line server in any language is enough to put a billion-row table in front of a reader.

11.2 Notable differences

A few places where lt works differently enough from gt to be worth spelling out, drawn from porting gsDesign2, gsDesign, and gsDesignNB. None of them is hard, but each is the kind of thing you only learn by tripping over it once, so consider this the cheaper way.

11.2.1 Column selection: strings or positions, not tidy-select

gt uses tidy-select, so unquoted column names and tidyselect helpers work. lt deliberately does not: it takes column names as character strings (or integer positions, or a one-sided formula). Tidy-select’s ergonomic win is mostly at the console. The cost is a large conceptual surface (data masking, quosures, injection) and painful programmatic use: the moment a column name comes from a variable, you are into {{ }} and all_of() machinery. For a package whose calls are often generated from code, plain strings win, so that is what lt takes.

# gt
tab_spanner(label = "Bounds", columns = c(alt, null))
# lt
lt_spanner(label = "Bounds", columns = c("alt", "null"))   # quote them
lt_spanner(label = "Bounds", columns = c(4, 5))            # or use positions
lt_spanner(Bounds ~ alt + null)                            # or a (compact) formula

If you dislike quoting names, the formula interface keeps them bare: Bounds ~ alt + null puts the label on the left and the columns on the right, the same as label = "Bounds", columns = c("alt", "null"). It relies only on base R’s formula, with no non-standard evaluation machinery: the names stay unevaluated symbols you can read off directly. Non-syntactic names work too, quoted in backticks: Bounds ~ `Alternate hypothesis` + `Null hypothesis`.

The formula also does duty for tidy-select predicates. In lt_format(), lt_align(), and friends, a one-sided formula whose right side is a logical expression selects the columns for which it is TRUE, with . bound to the vector of column names. So gt’s “all columns but one” idiom translates cleanly:

# gt: format every numeric column
fmt_number(columns = where(is.numeric), decimals = 4)
# lt: select by name, not by type
lt_format(~ . != "Metric", decimals = 4)   # every column except Metric

Note what is being tested. where(is.numeric) inspects each column’s values (its type), whereas the lt formula sees only the column names in .. There is no name-based way to say “the numeric ones”, so pick out the columns you do not want to format by name (often the single label column) and negate, or list the ones you do. (Tables already format numeric columns on their own, so you may not need lt_format() at all; see 2.1.)

11.2.2 Interactivity is one function, not a separate step

gt turns on client-side interactivity with opt_interactive(). lt folds all of it into lt_interactive(): sorting, searching, filtering, paging, resizing, row detail, profiles, a CSV or RTF download, and a reader-togglable column menu. Whatever you do not ask for is not loaded, so non-interactive tables cost nothing extra (7).

11.2.3 Footnotes and source notes are two different functions

gt::tab_footnote() does double duty: with a location it attaches a footnote to cells; without one it adds a general note. lt splits these:

  • lt_footnote(text, where, columns, rows, match) attaches a footnote to a location and gives it a marker. text is the first positional argument (not the location). where is one of "title", "subtitle", "column", "spanner", "group", "body". For "column" and "spanner" pass the name(s) in columns (names, positions, or a formula); for "body" also pass rows; for "group", match is "exact" (the default), "starts_with" to match a group label by prefix, or "all" for every group.
  • lt_note(text) adds a plain table note at the bottom. It is also the replacement for tab_source_note().

11.2.4 Row groups: lt_group(~ col), and two rendering styles

gt groups either via gt(groupname_col=) or a preceding dplyr::group_by(). In lt, grouping is a separate step, lt_group(~ col), with a one-sided formula for the grouping column.

There are two rendering styles, chosen by sep:

  • Separator rows: the group label sits on its own full-width row above the group. This is gt’s default; in lt you request it with sep = TRUE.
  • Rowspan: the group value is a merged cell down the left. This is gt’s row_group_as_column = TRUE; in lt you request it with sep = FALSE.

lt’s default is neither: sep = "auto" picks rowspan for short labels and separator rows when a single character grouping column has any label longer than about 20 characters. So a gt table will not necessarily match out of the box. Set sep explicitly if you need a specific style.

# gt default (separator rows)
x |> group_by(Analysis) |> gt()
# lt equivalent
lt(x) |> lt_group(~ Analysis, sep = TRUE)

You can also group by more than one column, lt_group(~ a + b), which nests the groups as rowspan cells (a spanning b). Separator rows work for a single column only, so multi-column grouping always renders as rowspan. This is a real difference from gt, which has only one level of row groups: groupname_col takes a single column, and multiple grouping variables are flattened into one combined label (joined by row_group.sep, default " - ") rather than nested.

Groups from row conditions, and controlling their order. gt can define groups on the fly from row predicates (a tab_row_group(label=, rows=<cond>) per group) and then set their order with row_group_order(). lt has no predicate form: it groups only by the value of an existing column. So the port is to materialize that column first. Build a factor whose levels are the group order you want (e.g., with data.table::fcase() or nested ifelse()), sort the data by it, and group on it with sort = FALSE so that lt keeps your row order instead of re-sorting the labels alphabetically:

# gt: groups defined by conditions, ordered explicitly
tab_row_group(label = "Power",  rows = Metric == "Power") |>
tab_row_group(label = "Events", rows = grepl("Events", Metric)) |>
row_group_order(groups = c("Events", "Power"))

# lt: derive an ordered factor column, then group by it
df$Group = factor(
  ifelse(grepl("Events", df$Metric), "Events", "Power"),
  levels = c("Events", "Power")          # desired group order
)
df = df[order(df$Group), ]
lt(df) |> lt_group(~ Group, sep = TRUE, sort = FALSE)

sort = FALSE is the key. By default lt_group() sorts rows by the grouping value, which would discard the factor order you set. With it off, the groups appear in first-seen row order, i.e., the factor-level order you sorted into.

If all you need is to reorder groups that already exist, you do not need a factor: a second lt_group() call with the labels in the order you want does it, and lt_group("Label" = rows) defines groups by hand from row numbers (3.4.1).

11.2.5 Raw HTML: I() is the new html() and md()

To keep raw HTML (e.g., a line break) from being escaped in a title, column label, or footnote, wrap it in I():

lt_label(theta = I("Underlying<br>response rate"))

I() is also the answer to gt’s md(). gt lets you wrap a title or label in md("**bold**") to render Markdown; lt has no Markdown-in-labels equivalent. Pass plain text (the common case: md("**Power**") simply becomes "Power"), or, if you truly need formatting, use I() with raw HTML: I("<b>Power</b>"). For body cells, mark whole columns with lt_html() (4.3).

11.2.6 Substitutions: the defaults already do the work

Two lt_sub() defaults are worth knowing before you translate a sub_*() call. Missing values already render as an em dash (—), and nothing special is done to zeros or small values. So a sub_missing(missing_text = "—") in gt is usually just noise in lt: drop it unless you want a different placeholder, set per column with lt_sub(columns, missing = ) or table-wide with the lt.missing option (see ?lt).

11.2.7 Styling: you probably don’t need CSS

lt’s default look is close to gt’s out of the box, so you rarely need CSS just to reproduce gt‘s base appearance. The whole stylesheet (lt.min.css) is only a couple of kilobytes, and it is deliberately unopinionated: it sets borders, spacing, and alignment, but does not impose a font-family or a table-wide font-size (only the title and subtitle get relative sizes). It inherits the surrounding page’s typography instead.

Because it declares so little, you can override or extend it with a few plain CSS rules, with no need to fight a heavy default. Add them with lt_css() and lt_style() (6), or just drop a <style> element or a chunk into your document, e.g.:

.lt-table { font-size: 0.9em; width: 100%; }

11.2.8 What lt does not have

A few gt features have no lt counterpart:

  • summary_rows() and grand_summary_rows(): compute the summary in R and append it as ordinary rows (lt_indent() and lt_style() can set them apart).
  • data_color(): use lt_style(test = , class = ) with a rule from lt_css() for conditional colors, or lt_errorbar()/lt_dotplot() for visual encoding.
  • opt_row_striping() and similar opt_*() themes: a few CSS rules, scoped to one table with lt_wrap(class = ).
  • tab_stubhead(): relabel the first column with lt_label().

11.3 Generating a static HTML table

By default an lt table is built in the browser by the JavaScript runtime (10) at view time, which is perfect for HTML pages but useless for output that must already contain the finished <table>: a GitHub README.md, an email, a cached page. lt_export(x, file) bakes the table into static HTML instead, running the runtime once at export time (it can also write images and other formats, depending on the file extension). Because it runs the runtime, baking needs a JavaScript engine: either Node.js or a headless browser (e.g., Chrome, Chromium, or Edge).2

In a knitr or litedown document you do not need to call lt_export() per table: set options(lt.lt_static = list(...)) and every lt() chunk in the document is baked with those arguments automatically (9.2). Outside such documents the option does nothing, and you must call lt_export() explicitly.

That option is how gsDesign2 turns README.Rmd into a README.md that GitHub renders with real tables. The trick is a custom knit field in the YAML header: it enables static baking, then knits directly with knitr::knit() instead of going through Pandoc. Pandoc would otherwise reformat the baked table, inserting extra blank lines inside it; GitHub then reads those blanks as paragraph breaks and wraps each cell’s content in a <p>, adding ugly large margins inside every cell.

---
# Use knitr::knit() directly to avoid pandoc reformatting raw HTML tables.
knit: |
  (function(inputFile, encoding) {
    options(lt.lt_static = list(fragment = TRUE, css = FALSE))
    output = knitr::knit(inputFile, encoding = encoding)
    body = xfun::yaml_body(xfun::read_utf8(output), parse = FALSE)$body
    body = body[cumsum(nzchar(body)) > 0]
    xfun::write_utf8(body, output)
  })
---

With that header, each lt(data) chunk in the README emits a finished <table> straight into README.md, with no post-processing needed.

12 Building on lt

Sooner or later, a package author wants to print their own objects as tables: a model summary, a design object, a study result. This chapter is for you. The good news is that lt was built to be extended, and the whole recipe fits on one page.

12.1 Why lt() is an S3 generic

gt::gt() is not an S3 generic; it is a plain function. A package that wants gt()-style output for its own object classes therefore has nowhere to hang a method. Both gsDesign and gsDesign2 worked around this the same way: each declared its own as_gt() generic,

as_gt = function(x, ...) UseMethod("as_gt")
as_gt.fixed_design = function(x, ...) { ... }
as_gt.gs_design    = function(x, ...) { ... }

This is awkward. Every package invents a differently named entry point (as_gt(), as_flextable(), as_kable(), …), so users must learn a new verb per package. Two packages can even define clashing as_gt() generics that mask each other on the search path. And none of it composes: there is no single function you can call on “whatever table-like object I have”.

lt takes the boring, standard route instead. lt() is an S3 generic:

lt = function(data, ...) UseMethod("lt")

Extending it to a custom class means defining a method. Users then call the one verb they already know, lt(x), on any object, yours included. No new generic, no name collisions, and summary() |> lt() reads the same everywhere.

12.2 Shipping lt methods from your package

The pattern gsDesign2 and gsDesign settled on has two steps.

  1. Re-export the generic, so that users can call lt() without attaching lt via library(lt) or writing lt::lt(). Re-exporting puts lt() in your package’s namespace.
  2. Define lt.<class>() methods for your summary or result classes. With the generic re-exported into your namespace, each method is registered with a plain #' @export.

Here is a sketch, adapted from gsDesign2’s as_lt.R:

# re-export the lt() generic so that users can call lt() without attaching
# lt via library(lt) or qualifying it as lt::lt()
#' @importFrom lt lt
#' @export
lt::lt

# in R/as_lt.R; with the generic re-exported into your namespace, each method
# can be registered with a plain #' @export
#' @export
lt.fixed_design_summary = function(data, title = NULL, footnote = NULL, ...) {
  if (is.null(title))    title    = attr(data, "title")
  if (is.null(footnote)) footnote = attr(data, "footnote")
  ans = lt::lt(as.data.frame(data), ...) |> lt::lt_header(title = title)
  if (!isFALSE(footnote))
    ans = lt::lt_footnote(ans, footnote, where = "title")
  ans
}

#' @export
lt.gs_design_summary = function(data, ...) {
  lt::lt(as.data.frame(data), ...) |>
    lt::lt_group(~ Analysis, sep = TRUE) |>
    lt::lt_spanner(
      label = "Cumulative boundary crossing probability",
      columns = c("Alternate hypothesis", "Null hypothesis")
    ) |>
    lt::lt_format(
      c("Z", "~HR at bound", "Nominal p",
        "Alternate hypothesis", "Null hypothesis"),
      decimals = 4
    )
}

Users then write fixed_design_ahr(...) |> summary() |> lt() in place of ... |> summary() |> as_gt(). The full version in gsDesign2 drives the title, subtitle, spanner, per-location footnotes (where = "group", "body", "spanner"), bound selection, and column selection all from arguments.

A few habits make such methods pleasant to use:

  • Return the lt table, not HTML. Let the caller add more verbs (lt_style(), lt_interactive(), …) before the table is printed. A method is a table builder; printing is somebody else’s job.
  • Pass ... on to lt(), as above, so that auto_format, auto_label, and show_types stay available to the caller.
  • Put sensible defaults in arguments (a title, a footnote) rather than hard-coding them, and let the caller switch them off.

12.3 Embedding tables in other widgets

Methods return tables for R to print. If instead you need an lt table inside another HTML widget (a reactable cell, a tooltip, a custom htmlwidget), use lt_spec() and lt_dependency() to ship the table as JSON and render it in the browser with LT.render(). That story is told in 9, and the JavaScript side in 10.

  1. HTML-first does not mean HTML-only for your final artifacts. lt_export() renders a table to PDF or PNG (via a headless browser), static HTML, CSV, or RTF, so you can still drop an lt table into a paper or slide deck. It just builds those from the HTML rather than from a separate rendering backend (see 9). ↩

  2. This does not undercut lt‘s lightweight promise. The engine is an opt-in runtime tool, not an install dependency: installing lt still pulls in only xfun. You need Node or a browser only on the occasional static-export path. The common cases (HTML pages, Shiny, litedown, pkgdown) render client-side in the browser the reader already has, needing nothing extra. And a headless browser is present on nearly every machine, while Node is a cheap, pure-tooling install. Contrast gt, which pulls in the V8 JavaScript engine unconditionally at install time (via juicyjuice, a plain Imports), and for a different purpose: gt builds the table in R and uses V8 to inline its CSS into per-element style= attributes. lt needs no such step. It links or embeds its tiny stylesheet (or omits it with css = FALSE). Keeping the styles in a stylesheet is also easier to customize: inline style= attributes carry high specificity, so a reader’s own stylesheet cannot override them without !important or editing the markup, whereas an ordinary rule can restyle an lt table freely. (Inlining is genuinely useful for email, where <style> blocks are often stripped. It is the right tool there, just not a good default elsewhere.) ↩
